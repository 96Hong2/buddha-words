# 실제 모델과 그것을 고른 근거

측정일 2026-09-15. 1차 패스와 2차 패스만 2026-09-16 에 다시 쟀다. 측정자가 직접 돌린
값이고, 실행 출력에서 기대값을 베껴 오지 않았다. 프롬프트는 이 폴더의 `prompts.py` 그대로다.
프롬프트를 고치면 이 표는 다시 재야 한다.

실제로 그 일이 있었다. 프롬프트를 고친 뒤 표를 그대로 두어 값이 낡아 있었다. 실제로 부르는
두 자리(1차 패스 · 2차 패스 DEEP)를 붙여 다시 쟀고, 결과는 「프롬프트를 고친 뒤 다시 잰
값」 절에 있다. **분류 · LIGHT · 위로 답변 세 자리와 모델 다섯을 견준 표는 이번에 다시 재지
않았다.** 그것들은 2026-09-15 프롬프트로 잰 값이라 모델을 고른 근거로만 읽는다.

모델 id 는 **배포 산출물**이라 `openai.py` 상수로 박는다. 환경변수로 고르는 것은
provider(`stub`|`openai`)와 API 키뿐이다(앱인토스 AI 운영 요건 4번).

등급 상수를 셋으로 남겨 둔 것은 계획 1.3 절의 등급 계약이 살아 있기 때문이다. 나중에

## 2026-09-15 에 뒤집은 것

그 전에는 `cheap` 에 gpt-5.4-mini, `premium` 에 gpt-5.6-luna 가 박혀 있었다.
**mini 가 luna 보다 3.75배 비싸서 등급 이름과 값이 뒤집혀 있었다.** 그래서 예산 문이
닫혔을 때의 `premium → cheap` 강등이 값을 줄이지 못하고 오히려 올렸다. 기동 로그가
`budget_downgrade_costs_more` 경고로 매번 그 사실을 알리고 있었다.

싼 모델을 `cheap` 에 놓는 것으로 고쳤고, 그 결과 강등이 실제로 값을 내린다(아래

프롬프트가 바뀌어 낡았고, 지금 값은 「프롬프트를 고친 뒤 다시 잰 값」 절에 있다. 모델끼리의

고민 여섯 건으로 쟀다. 글은 `tests/data/retrieval_eval.json` 에 있는 것을 그대로 썼다.

## 위기 판정 문구를 고친 뒤 (2026-09-16, 통합 검수 2회차)

`CLASSIFY_SYSTEM` 의 crisis 갈래 설명과 `PASS1_SYSTEM` 의 `safetyFlag` 설명 두 곳을 고쳤다.
평범한 고민이 상담 창구로 가던 것을 막으려고 「끝내겠다는 대상이 삶인가」를 기준으로 넣었다.

**무엇을 쟀나.** 판정이 어디로 가는지를 쟀다. 값과 시간은 다시 재지 않았다.
프롬프트가 길어졌으니 입력 토큰이 조금 늘고, 위의 값 표는 그만큼 낮게 잡힌 값이다.

| 무엇 | 고치기 전 | 고친 뒤 |
| --- | --- | --- |
| 일상 고민 12개가 창구로 잘못 가는 비율 | 3 / 36 (다이어트 글 한 개가 3회 모두) | 0 / 120 |
| 위기 글 8개가 창구로 가는 비율 | 24 / 24 | 80 / 80 |
| 예산 문이 닫혔을 때 위기 글이 창구로 가는 비율 | 6 / 16 | 24 / 24 |

세 줄 모두 실제 모델(gpt-5.6-luna)에 붙여 `/concern` 을 친 값이다. 위기 글은 직접 죽음을
말하는 것 셋, 에두른 것 셋, 학대 하나, 자해 하나다.

**다시 재야 하는 것.** 이 절은 판정만 본다. 1차·2차 패스의 값과 시간, 접두 캐싱 적중률은
프롬프트가 바뀌었으니 아래 표들이 낡았다. 릴리즈 전에 「다시 잴 때」 절이 적은 대로 한 번 더 돌린다.

## 프롬프트를 고친 뒤 다시 잰 값 (2026-09-16)

프롬프트를 고쳐 놓고 표를 다시 재지 않아 값이 낡아 있었다. 실제로 부르는 두 자리를
gpt-5.6-luna 로 다시 쟀다. 모델은 바꾸지 않았으니 여기는 모델 고르기가 아니라 **지금
값이 얼마인가**를 적는 절이다.

**어떻게 쟀나.** 두 회차로 나눠 각각 새 고민 6건씩, 모두 12건이다. 글은
`tests/data/retrieval_eval.json` 의 것을 그대로 썼고 1회차와 2회차가 서로 겹치지 않는다.
겹치면 프롬프트 전체가 캐시에 걸려 값이 실제보다 싸게 나온다. 후보 20개는 실제 검색
경로(`compose.candidate_pool`)로 뽑았고, 2차 패스는 1차 후보의 첫 구절을 DEEP 분량으로
넣었다. 등급은 1차 cheap · 2차 premium 인데 세 등급이 같은 모델이라 값은 등급과 무관하다.

세는 방식도 밝혀 둔다. **로그를 grep 으로 세지 않았다.** `llm_call` 한 줄에 이름이 두 번
나와서(`message` 와 `event`) 세는 방식에 따라 두 배가 된다(「로그만 보고 확인하는 법」
절에 실제 출력을 적어 두었다). 로깅 핸들러를 붙여 레코드 자체를 받아 세었다. 아래 값은 그
레코드의 `ms` · `tokens_in` · `cached_in` · `written_in` · `tokens_out` · `usd` 다.

들어오는 자리의 값이고, 새 고민마다 내는 값은 위의 두 표다.

## 프롬프트 접두 캐싱 (2026-09-15 확인)

OpenAI 는 프롬프트 앞부분이 그대로 반복되면 그 토큰을 **정가의 10%** 로 청구한다.
자동이고 따로 켜지 않는다. 문턱은 gpt-5.6 세대에서 **보이는 입력 1,024토큰**이고,
고정된 것을 앞에, 변하는 것을 뒤에 두어야 한다.

### 배치는 이미 맞다

`prompts.py` 는 고정 지시를 전부 **system 메시지**에 두고, 고민 글과 경전 후보 같은
변동분을 **user 메시지**에 둔다. 캐시가 먹는 순서 그대로다. 고칠 것이 없었다.

user 메시지 꼬리에 고정 문장이 조금 남아 있다(1차 패스의 「이 목록 밖의 id 를 적지
마세요」 14토큰, 2차 패스의 분량 지시 67토큰). 변동분 뒤라 캐시에는 안 잡히지만,
옮겨서 아끼는 값이 한 번에 $0.000003~0.0000134 다. 그 자리에 있는 것이 모델의 준수율에
도움이 되는 문장들이라 **옮기지 않았다.**

### 실제로 먹는지 본 값

서버 로그 `llm_call` 의 `cached_in` 이 그날 찍은 값이다.

| 자리 | 문턱 통과 | luna 캐시 (2026-09-15) | luna 캐시 (2026-09-16 재측정) |
| --- | --- | --- | --- |
| 1차 패스 | 통과 | 1,167 | **1,365 · 1,465** (회차마다 다름) |
| 2차 패스 | 통과 | 1,032~1,034 | **1,112** (12건 모두 같음) |
| classifier | 미달 | 0 | 재지 않음 |
| LIGHT | 미달 | 0 | 재지 않음 |
| 위로 답변 | 미달 | 0 | 재지 않음 |

같은 고민이 연달아 들어오면 고정 접두만이 아니라 **고민 글까지 포함한 프롬프트 전체**가
걸린다. 2026-09-16 재측정에서 1차 패스 3,690토큰 중 3,687토큰이 캐시로 읽혔다. 위 표는
새 고민마다 걸리는 몫이고, 저 값은 다시 보기나 재시도처럼 같은 글이 이어 들어올 때의 몫이다.

1차 패스는 입력이 값의 대부분이라 효과가 크다. 같은 고민을 두 번 넣었을 때 한 번 값이
$0.000862 에서 **$0.000301** 로 내려간다(캐시 쓰기까지 센 값).

#### 「mini 는 캐시를 못 잡는다」는 틀렸다 [2026-09-15 정정]

이 자리에 한동안 「gpt-5.4-mini 는 같은 접두에도 캐시를 한 번도 잡지 못했다. 캐싱은 5.6
세대로 옮긴 것만으로 켜졌다」가 luna 를 고른 이유 하나로 적혀 있었다. **재현되지 않는다.**
같은 1차 패스 프롬프트를 두 모델에 각각 두 번씩 넣어 다시 쟀다.

| 모델 | 1회 캐시 | 2회 캐시 | 1회 값 | 2회 값 |
| --- | --- | --- | --- | --- |
| gpt-5.6-luna | 1,167 | 3,591 | $0.000926 | $0.000327 |
| gpt-5.4-mini | 0 | 3,328 | $0.004059 | $0.001520 |

mini 도 캐시를 잡는다. 처음에 0 이 찍힌 것은 모델이 캐시를 못 해서가 아니라 **그 프롬프트를
그 모델에 처음 보냈기 때문**이다. luna 쪽은 앞선 측정으로 접두가 이미 데워져 있었다.
데워진 쪽과 식은 쪽을 맞대 놓고 세대 차이라고 읽은 것이 틀렸다.

고른 결과는 그대로다. 캐시가 양쪽에 다 걸린 뒤에도 luna 가 **4.6배** 싸다(식은 상태에서는
4.4배). luna 를 고른 이유는 캐싱이 아니라 단가 자체다.

### 문턱을 못 넘는 세 자리는 그냥 둔다

classifier 접두는 1,024토큰에서 약 90토큰 모자란다. 채워 넣으면 캐시가 켜져 분류 한 번
값이 $0.000244 에서 $0.00008 언저리로 내려간다는 **계산이다. 확인한 값이 아니다.**
같은 분류 프롬프트를 세 번 연달아 넣어 봤는데 전체가 1,025토큰인데도 `cached_in` 은
세 번 다 0 이었다. 문턱을 1토큰 넘기는 것으로는 켜지지 않는다. 채우기로 한다면 얼마나
넘겨야 켜지는지부터 재야 한다. **이번에도 하지 않았다.** 문턱을 넘기려고 쓸모없는
글자를 채우는 것은 프롬프트를 나쁘게 만들고, 가격 정책이 바뀌면 그대로 쓰레기가 된다.
분류에 쓸모 있는 예시를 더 넣어 자연스럽게 넘기는 길이 있고 위의 경계 문제도 같이 손볼
수 있지만, 그것은 프롬프트 품질 작업이라 따로 재야 한다. 계획 문서에 남겨 두었다.

### 예산 문도 캐시 값으로 센다

`Spend.of` 가 입력 토큰을 세 몫으로 갈라 센다. 응답의 `prompt_tokens_details` 가
`cached_tokens` 와 `cache_write_tokens` 를 주고, 둘 다 `prompt_tokens` 안에 든 값이라
겹치지 않게 잘라 쓴다. 나머지가 정가다.

| 몫 | 단가 | 1차 패스 새 고민 12건 (2026-09-16) |
| --- | --- | --- |
| 캐시에서 읽은 것 | 정가의 10% | 1,365 또는 1,465토큰 |
| 캐시에 올린 것 | 정가의 1.25배 | 2,250~2,490토큰 |
| 나머지 | 정가 | 3토큰 (12건 모두) |

정가로 나가는 몫이 3토큰뿐이다. 새 고민마다 값을 만드는 것은 사실상 **캐시에 올리는 칸**
하나이고, 그 칸이 정가보다 비싸다. 여기를 빼고 세면 예산 문이 덜 썼다고 본다.

두 번 고쳤다. 전부 정가로 세던 첫 셈은 1차 패스에서 실제보다 **30% 가까이 많이** 썼다고
봐서 필요 없는 강등을 일으켰다. 캐시 읽기만 세고 쓰기를 빼던 다음 셈은 거꾸로 **15% 적게**
썼다고 봤다. 한쪽만 세면 예산 문이 틀린 값으로 강등을 정한다.

## 예산 강등을 실제로 태워 본 값 (2026-09-15)

같은 DEEP 고민 네 건을 예산 ok 와 warn 에서 각각 태웠다. 다른 것은 임계값뿐이다.
두 번 쟀다. 두 번째는 고민마다 A→B 와 B→A 를 번갈아 돌려 **순서에 따른 캐시 이득**을
지웠다. 먼저 도는 쪽이 캐시를 데워 주므로 한 방향으로만 돌리면 뒤쪽이 싸게 나온다.

| | 예산 상태 | `routeNote` | 관점 수 | 분량 | 상담 한 건 값 | 순서 균형 재측정 |
| --- | --- | --- | --- | --- | --- | --- |
| A | ok | 없음 | 3 | 1,311~1,423자 | $0.002358 | $0.001723 (1,208~1,407자) |
| B | warn | `downgraded_budget` | 1 | 754~865자 | **$0.001343** | **$0.001093** (688~850자) |

**강등이 값을 37~43% 내린다.** 고치기 전에는 같은 장치가 값을 2.4배로 올렸다.
낮은 쪽(37%)이 순서 균형을 맞춘 값이니 그쪽을 믿는다. 재측정에서도 네 건 모두
`routeNote: downgraded_budget` 이 붙고 관점이 3에서 1로, 로그의 `tier` 가 premium 에서
cheap 으로 바뀌었다.

한 가지 밝혀 둔다. **값을 내리는 것은 모델을 바꿔서가 아니다.** 세 등급이 같은 모델이라
`premium → cheap` 강등은 모델을 그대로 둔다. 실제로 값을 내리는 것은 `compose_pass2` 가
분량 지시도 같이 내리는 것(`deep=False`)이고, 출력 토큰이 1,400대에서 800대로 줄어서
값이 내려간다. 출력 단가가 입력의 6배라 분량이 값을 지배한다.

기동 로그의 `downgrade_effect` 필드가 이 사실을 그대로 싣는다. 지금 값은 `same_model` 이다.

## 상담 한 건 값, 고치기 전과 후

같은 서버·같은 경로로 재고 서버 로그의 `usd` 를 합쳤다.

| 상담 갈래 | 고치기 전 | 고친 뒤 | |
| --- | --- | --- | --- |
| NORMAL (분류 + 1차 + 2차) | $0.008705 | **$0.001756** | **−80%** |
| DEEP (분류 + 1차 + 2차 deep) | $0.003184 | **$0.002358** | **−26%** |

NORMAL 이 크게 내려간 것은 세 자리가 모두 gpt-5.4-mini 였기 때문이다. DEEP 은 1차·2차가
원래도 luna 였고 분류만 바뀌어서 차이가 작다.

DEEP 의 「고치기 전」 값은 재서 합친 것이다. 같은 고민을 두 매핑에 연달아 넣으면 뒤에
도는 쪽이 캐시를 그대로 받아 값이 흐려져서, 분류 실측값($0.001076)에 1차·2차 실측값을
더했다. NORMAL 은 두 매핑이 각각 캐시가 찬 정상 상태에서 잰 값이라 그대로 적었다.

**이 표는 2026-09-16 에 다시 재지 않았다.** 합계에는 분류가 들어 있는데 분류는 이번에 재지
않았고, 재지 않은 값과 다시 잰 값을 섞어 더하면 어느 쪽도 아닌 숫자가 나온다. 1차·2차만
새 값으로 놓으면 DEEP 의 두 자리 합이 $0.002231 에서 $0.002407 로 오른다(1차 $0.000862 +
2차 $0.001545). 상담 한 건 값 전체가 필요하면 분류까지 같은 회차로 다시 재야 한다.

## 로그만 보고 확인하는 법

`llm_call` 한 줄에서 자주 보는 값은 여섯이다. 여섯 다 세는 값이고 글은 담지 않는다.

**호출 수를 셀 때 조심할 것이 있다.** 한 줄에 `"message": "llm_call"` 과 `"event": "llm_call"`
이 둘 다 실려서 이름이 두 번 나온다. 줄을 세는 `grep -c llm_call` 은 1 로 맞지만, 나온
횟수를 세는 `grep -o llm_call | wc -l` 은 2 가 된다. 실제로 확인한 값이다.

```
$ grep -c llm_call server.log        # 1  ← 줄을 센다. 맞다
$ grep -o llm_call server.log | wc -l  # 2  ← 나온 횟수를 센다. 두 배다
```

세려면 `grep -c '"event": "llm_call"'` 처럼 한 필드를 집어 세거나 로깅 핸들러로 레코드를
직접 받는다.

| 필드 | 뜻 | 정상값 |
| --- | --- | --- |
| `candidates` | 1차 패스에 실은 경전 후보 수 | **20.** 400 이면 좁히는 자리가 끊긴 것이다 |
| `tier` | 그 호출이 고른 등급 | DEEP 은 premium, NORMAL 은 cheap, Extension 은 standard |
| `chars_in` | system + user 프롬프트 글자 수 | 1차 패스 5,800~6,400 · 2차 DEEP 2,000~2,300. 만 단위면 후보가 안 잘렸다 |
| `cached_in` | 캐시에서 읽은 입력 토큰 | 1차 1,300~1,500 · 2차 1,110 언저리. **0 이 계속이면 캐싱이 끊겼다** |
| `written_in` | 캐시에 올린 입력 토큰 | 새 고민마다 1차 2,250~2,520 · 2차 220~380. 정가보다 비싼 칸이다 |
| `usd` | 그 호출에 쓴 달러 | 1차 $0.0009 언저리 · 2차 DEEP $0.0015 언저리 |

정상값은 2026-09-16 에 두 사람이 각각 12건씩 잰 폭을 합친 것이다. 24건으로 잡은 폭이라
한두 건이 살짝 밖으로 나가는 것은 이상이 아니다. 보는 것은 자릿수와 0 이 이어지는지다.
프롬프트를 고치면 여기도 같이 고친다.

`tier` 를 따로 남기는 이유가 있다. 세 등급이 같은 모델 id 라 모델 이름만으로는 어느
등급으로 불렀는지 가릴 수 없다.

기동 로그 `llm_provider` 한 줄에는 등급 셋의 모델 id 와 `downgrade_effect` 가 실린다.
`costlier` 가 찍히면 등급과 단가가 또 뒤집힌 것이고 `budget_downgrade_costs_more`
경고가 함께 뜬다.

## 다시 잴 때

```bash
set -a && . ./backend/.env && set +a
cd backend && LLM_LIVE=1 .venv/bin/pytest -q tests/test_llm_openai.py
```

`tests/test_llm_openai.py` 의 live 표시가 붙은 검사 넷이 다섯 메서드를 실제로 부르고,
등급 셋에 박힌 모델 id 가 살아 있는지 확인한다. 키가 없으면 건너뛴다.

단가와 등급이 어긋나는 것은 live 없이도 걸린다. `test_budget_downgrade_never_costs_more`
와 `test_tier_prices_do_not_invert` 가 평소 pytest 에서 돈다.

live 검사는 다섯 자리가 살아 있는지만 본다. **값과 지연 표를 다시 채우려면 따로 돌려야
한다.** 2026-09-16 재측정은 한 번 쓰고 버린 스크립트로 했고, 하는 일은 이것뿐이다.

1. `tests/data/retrieval_eval.json` 에서 서로 겹치지 않는 고민을 회차마다 6건씩 고른다
2. 후보 20개를 실제 검색 경로(`compose.candidate_pool`)로 뽑는다
3. `OpenAIClient.pass1` 과 `pass2(deep=True)` 를 그 값으로 부른다
4. `app.integrations.llm.openai` 로거에 핸들러를 붙여 `llm_call` 레코드를 그대로 받는다
5. 지연·토큰·캐시·값은 중앙값과 최소~최대로 요약한다

2차 패스 분량은 `openai.answer_length` 를 감싸서 받았다. 분량 하한에 걸려 다시 만든 호출이
있었는지는 `llm_length_retry` 로그 줄 수로 본다.
