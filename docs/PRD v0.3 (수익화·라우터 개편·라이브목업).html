01

한 줄 정의와 승부처

이 앱이 이기거나 지는 자리는 두 화면이다. 나머지는 그 둘을 받치는 장치다.

성공 기준은 퍼널이다. 「불교 느낌이 예쁜 앱」이 아니다. 장난으로 들어온 사람이 「그냥 장난으로 들어왔는데 답이 꽤 괜찮네」 → 「내 진짜 고민도 써볼까」 → 「이건 저장하고 싶다」 → 「친구한테 이 문장은 보내고 싶다」로 흐르는 것. 모든 화면·광고·라우팅 결정을 이 퍼널로 다시 검토했다.

성공 가설. 사용자는 좋은 명언이 아니라 「내 상황을 제대로 이해했다고 느끼는 답변」 때문에 다시 온다. 그래서 이야기를 더 쓰게 만드는 입력 화면과, 그 이야기를 읽었다는 것이 증명되는 답변 화면에 개발 시간을 몰아넣는다. 그리고 첫 답변은 광고 없이 준다.

승부처 A

고민 입력 화면

「여기에 정말 내 이야기를 적어도 되겠다」고 느끼게 만드는 화면. 빈칸 공포를 예시 칩이 없애고, 인디케이터가 더 쓸 이유를 만든다. 억지로 늘리라고 부탁하지 않고 무엇이 좋아지는지를 말한다.

승부처 B

답변 화면

「어, 이거 생각보다 제대로 답하는데」로 만드는 화면. 마음 태그가 내 문장에서 나왔다는 것이 보이고, 경전이 실제 출처를 달고 있고, 가장 긴 블록이 내 상황을 그대로 다룬다.

승부처를 받치는 것

경전 데이터

화면 B는 경전 데이터가 없으면 껍데기다. 그래서 감수를 끝낸 법구경 120구절을 화면 B보다 먼저 세운다. 데이터가 병목이라는 사실을 일정에 그대로 적었다.

사용자가 앱을 여는 순간

연애로 마음이 복잡할 때, 회사 사람 때문에 화가 났을 때, 미래가 불안할 때, 남과 비교하게 될 때, 돈이 걱정될 때, 아무것도 하기 싫을 때, 선택을 못 하겠을 때. 이때 원하는 것은 「집착을 버리세요」가 아니라 내 이야기를 읽고 이해한 다음, 왜 이런 마음인지 설명해 주고, 그래서 지금 어떻게 하면 좋을지 알려 주는 것이다.

X13 · 답변 블록

X14 · 보관함

X15 · X16 · 다시 올 이유

X17 · 위기 화면

짧고 담백하게

탐지 로직은 그대로. 화면은 제목 두 줄 + 109 + 마들랜 + 닫기·다른 이야기 쓰기로 한 화면 안. 그림 없음. 온보딩·홈에 위기 문구 없음.

고해상 자세 6종 × 시간대 4

03

만드는 것과 안 만드는 것

P0 는 이것이 없으면 제품을 설명할 수 없는 것이다. 뺀 것은 지금 만들 수 없어서가 아니라, 다 넣으면 아무것도 안 나오기 때문에 뺐다. Activation → 통찰 → 광고/저장 → 재방문 → 공유 루프를 먼저 완성한다.

P0 · 첫 출시에 들어가는 것

입력

고민 입력과 3줄 유도

메인 카피, 자동 높이 입력창, 점 3개와 문구 3단계, 예시 칩 3개, 전송 버튼. AI 고지와 개인정보는 입력창 아래 작은 한 줄. 초안 임시저장 24시간.

수익

NORMAL 과 DEEP 을 맥락(이해관계자 수 · 결정 필요 · 구체성)으로 가르고 약한 위기 후보를 확정한다. CRISIS 는 어느 층이든 올리면 올라가고 내려오지 않는다. 분류기가 실패하면 위기 후보는 CRISIS, 나머지는 NORMAL 로 내려 답변은 나가게 한다.

글자 수만으로 DEEP 이 되지 않는다. 「ㅋㅋㅋㅋ」 열 줄은 LIGHT, 「힘들다」 서른 번은 INVALID, 「남편이 다른 사람을 만나는 것 같아요. 이혼해야 할까요?」는 22자여도 NORMAL 이상이다. 분류기 확신이 0.6 미만인 DEEP 은 NORMAL 로 내린다.

「3줄 = 고급 모델」처럼 구현을 노출하는 문구는 쓰지 않는다. 판정은 마스킹보다 먼저 한다. 전화번호 열한 자리를 먼저 가리면 두 글자가 된다.

왜 CC0 인가

한글 번역문은 원저작물의 2차적저작물이다. 남의 한글 번역을 그대로 쓰면 허락 없이는 배포가 안 된다. CC0 는 저작권자가 권리 자체를 포기한 것이라 그 위에 우리가 만든 한국어 번역은 우리 저작물이 된다. 라이선스가 문서로 확정되기 전에는 데이터베이스에 한 글자도 넣지 않는다.

코드가 세는 것

  • 감정 태그 10종 각각 감수 통과 구절이 10개 이상, 쉬운 구절이 4개 이상
  • 감수 통과 구절은 전부 감수자와 감수일이 채워져 있다
  • 기준본 셋이 갈린 것으로 표시된 구절은 주석이 비어 있지 않다
  • 직전 커밋보다 감수 통과 구절 수가 줄면 빌드가 실패한다
  • 번들에 팔리 원문 필드가 비어 있다
  • 코드가 막는 제외 조건의 값 집합이 1차 분류가 내는 플래그 목록 안에 있다
검색은 어떻게 도나

안전 스크린을 먼저 지난다. 걸리면 검색도 답변 생성도 하지 않는다. 통과하면 감정 태그로 거른 12~20개 후보를 전부 2차 패스에 넘긴다. 규칙 점수 단계는 없앴다. 관련성을 못 보는 규칙이 관련성 판단자보다 먼저 후보를 깎고 있었고, 네 항 중 셋이 변별력이 없어 결국 「덜 나간 순서」로 붕괴했다.

같은 구절이 연달아 나오지 않게 최근 노출 20개를 클라이언트가 들고 와 요청에 싣는다. 서버는 개수와 구절 id 화이트리스트로 검증한다. 인메모리 전역 카운터는 쓰지 않는다. 서버 인스턴스가 여럿이면 흩어진다.

임베딩과 pgvector 는 켜지 않는다. 120구절에서 태그 필터를 지난 후보가 12~20개라 더 줄일 것이 없다.

「이 구절은 이 사람에게 쓰지 않는다」를 두 층으로 나눈 이유

구절마다 사람이 읽는 주의사항과 코드가 막는 제외 조건을 따로 둔다. 앞의 것은 프롬프트에 실리고 뒤의 것은 후보 목록에서 아예 빠진다. 프롬프트에 적는 것과 코드가 막는 것은 다른 층이다. 프롬프트만 믿으면 뚫린다.

예를 들어 학대 피해 맥락에서는 「분노는 분노하지 않음으로 이긴다」가 참으라는 말로 읽힌다. 그래서 그 구절에 학대 피해 제외를 걸어 두고, 1차 분류가 그 플래그를 세우면 후보에서 빠진다. 이 짝이 실제로 맞는지는 골든셋 30건이 확인한다.

감수 품질을 무엇으로 확인하나

「감수했다」는 선언은 검증이 아니다. 감수자가 아닌 사람이 무작위 10구절을 뽑아 영역본과 나란히 읽었을 때 뜻이 어긋난 것이 0건이어야 한다. 1건이라도 나오면 그 구절이 속한 태그를 통째로 다시 본다. 읽은 사람과 날짜와 결과를 저장소에 남긴다.

감수 산출물은 저장소에 추적되는 파일로 둔다. 10~20시간의 결과가 누군가의 로컬에만 있으면 그 사람이 빠질 때 사라진다.

층은 둘이다. 앱 배경과 카드. 셋째 층을 밝기로 만들면 흙빛이 되어 에셋의 인상이 깨진다. 층이 하나 더 필요한 자리는 밝기가 아니라 선으로 나눈다.

12

기술과 아키텍처

읽지 않아도 제품을 판단할 수 있게 전부 접어 두었다. 필요한 것만 펼쳐 본다.

답변이 두 번에 오는 구조

요청 1 (3~5초). 결정론적 안전 스크린을 먼저 지나고, 1차 분류가 응답 종류·위기 플래그·맥락 플래그·감정 태그·핵심 한마디·구절 후보 id·그림 테마를 낸다. 서버가 그 구절 id 를 화이트리스트로 검증한 뒤 데이터베이스 원문으로 조립한다. 이때 상담 기록에 대기 행을 만들고 멱등키를 걸어 사용량을 예약한다.

요청 2 (약 20초). 클라이언트가 멱등키와 고민 원문을 다시 보낸다. 서버는 구절 id 를 클라이언트 값이 아니라 대기 행에서 읽는다. 클라이언트가 함께 보낸 id 가 그 행과 다르면 그 요청을 거부한다. 이렇게 해야 「우리가 준 범위 밖의 경전이 못 나간다」는 방어선이 두 번째 요청에서도 산다. 서버 세션은 없고 상태는 행 하나에만 있다.

대기 행에 남기는 값은 넷뿐이다. 구절 id 목록, 맥락 플래그, 위기 플래그, 판정 모드. 전부 id 와 열거값이라 고민 원문 미저장 원칙과 부딪히지 않는다. 행은 24시간 뒤 정리한다.

스트리밍과 부분 JSON 파서와 폴링을 전부 뺐다. 길이를 다시 만드는 일과 스트리밍은 같은 요청에서 양립하지 않고, 폴링은 서버 인스턴스가 여럿이면 돌지 않으며, 돌게 만들면 고민 원문이 프로세스 밖에 기록된다.

두 번째 요청만 실패했을 때

답변 전체를 실패로 보지 않는다. 상단 세 블록은 화면에 남긴다. 그 아래에 「나머지를 못 불러왔어요」 한 줄과 다시 시도 버튼을 붙인다. 재시도는 같은 멱등키로 두 번째 요청만 다시 부르고 사용량을 다시 깎지 않는다.

24시간 안에 완료되지 않은 행은 실패로 닫고 그때 사용량을 되돌린다. 보관함과 공유는 완료된 답변만 받는다.

이 처리가 정해져 있지 않으면 개발자마다 다르게 만든다. 그래서 한쪽으로 못 박았다.

사용량을 어떻게 세나

확인하고 나서 차감하면 그 사이에 들어온 요청이 전부 통과한다. 그래서 확인이 아니라 예약으로 바꿨다. 상담 기록에 대기 상태 행과 멱등키 유니크 제약을 먼저 넣는다. 같은 고민을 백그라운드 전환으로 세 번 동시에 쏴도 횟수는 하나만 줄어든다.

하루 3회 + 분당 2회 + 입력 2,000자 + 본문 크기 제한 + 전역 일일 예산 문. 하루의 기준 시각은 사용자 시간대 자정이다. 시간 값은 세계 표준시로 저장하고 날짜만 사용자 시간대로 뽑는다. 세계 표준시로 날짜를 뽑으면 자정부터 아침 아홉 시까지가 전날로 샌다.

예산 문은 숫자로 못 박았다. 하루 지출 $10 에서 경고 메일, $20 에서 새 요청 차단. 닫히면 조용히 죽지 않는다. 앱 정보 화면에 배지가 뜨고 홈 전송 버튼이 안내 문구로 바뀐다. 다음 날 자정에 자동으로 열린다.

안전을 두 층으로 나눈 이유

첫 층은 LLM 앞의 결정론적 키워드 스크린이다. 모델이 실패하거나 느려도 이 층은 언제나 돈다. 둘째 층은 1차 분류가 내는 위기 플래그다. 둘 중 하나만 걸려도 본 답변을 만들지 않는다.

이 이중화가 없으면 사고가 난다. 폴백 사다리가 1차 분류 실패를 「후보 0개」로 읽어 자해 고민을 일반 구절 풀로 보내는 경로가 실제로 있었다. 지금은 분류 실패를 별도 분기로 빼고 재시도한다.

응답 종류 필드를 1차 출력의 첫 자리에 둔다. 답할 수 없는 요청에는 고정 문구 집합에서 거절이 나간다. 스키마에 거절을 담을 자리가 없으면 우회 요청에 억지 답변이 나간다.

위기 화면의 나가는 길은 「닫기」와 「다른 이야기 쓰기」 둘뿐이다. 위기 입력이 본 답변 프롬프트에 닿는 경로를 코드에서 막는다.

모델과 프롬프트를 어디에 두나

모델 식별자와 프롬프트를 런타임 설정이 아니라 배포 산출물로 고정한다. 환경변수로 모델을 갈아 끼우는 경로를 없앴다. 「AI 모델이나 프롬프트를 바꾸면 사전 검토를 받는다」는 요건이 환경변수 교체·예산 강등·타임아웃 재시도를 전부 무효로 만들기 때문이다. 강등과 재시도는 심사에 함께 신고한 모델 쌍 안에서만 한다.

사후 검사에 걸린 답변과 사용자가 신고한 답변만, 가린 뒤, 7일 격리 보관한다. 답변 본문을 어디에도 안 남기면 「부적절한 응답을 즉시 수정·차단한다」는 요건을 못 채운다. 접근 기록을 남기고 처리방침에 적는다.

모델이 내는 값의 모양

v0.1 에서 바뀐 자리만 적는다.

  • scripture 를 모델이 채우지 않는다. 모델은 scriptureIds 만 낸다
  • responseType 이 1차 출력의 첫 필드다. 값은 답변 또는 거절
  • personalAnalysis 가 문자열 하나에서 {heading, body} 배열 2~3개로
  • actions 가 문자열 배열에서 {title, why} 배열로. 왜 그 행동인지가 붙어야 하루가 바뀐다
  • terms 0~2개 추가. 용어 풀이는 지어내지 않고 구절에 붙어 있는 해설에서 나온 말만 쓴다
  • contextFlags 추가. 코드가 막는 제외 조건과 값 집합이 일치하는지 빌드가 검사한다
  • coreMessage 에 40자 상한
어디서 가져다 쓰나

브릿지 경계, 제공자 계층, API 계층, 오류 바운더리, 뒤로가기 처리, 탭바, 배포 스크립트, CI 잡, 행동 로그를 기존 미니앱에서 그대로 복제한다. 도메인 코드는 가져오지 않는다.

서버는 컨테이너 하나와 관계형 데이터베이스 하나. 자동 백업을 켜고 오류율 알림을 등록한다. 모니터링이 없으면 예산 문이 닫혔을 때 앱이 죽은 채로 있는다.

검증 코드는 제품 저장소 안에 두되 커밋하지 않는다. 익명키 격리 장치가 첫 번째다. 그것이 없으면 두 번째 테스트부터 전부 횟수 제한에 걸린다.
