### 1.1 카피에 직접 걸리는 토스 UX 라이팅 규칙

원문 `[공식]` UI/UX 가이드 「UX 라이팅」 절.

| 규칙 | 나쁜 예 | 좋은 예 |
| --- | --- | --- |
| 해요체 | 답변이 생성되었습니다 | 답을 다 풀었어요 |
| 능동형, `~었` 빼기 | 도움이 되었나요 | 도움이 됐나요 |
| 긍정형 우선 | 오늘 무료 상담을 모두 사용했어요 | 내일 아침이면 다시 이야기할 수 있어요 |
| 과도한 경어 금지 | 이야기를 들려주셔서 | 이야기를 들려줘서 |
| `되어요` → `돼요` | 준비되어요 | 준비돼요 |
| 명사+명사 금지 | 깊은 풀이 준비 완료 | 깊이 풀어 드릴 수 있어요 |
| 다이얼로그 왼쪽 버튼은 **닫기** | 취소 | 닫기 |

> "**취소**는 사용자가 하고 있는 작업이 취소된다고 오해할 수 있어 쓰지 않아요" `[공식 원문]`

| D14 | **초안은 `Storage`(네이티브 영속 저장소)에 두고 24시간 뒤 버린다** | 웹뷰 저장소가 비워질 수 있다 `[SDK]`. 고민 원문이 남의 폰에 계속 남아 있는 것 자체가 위험 | localStorage 영구 보관: 값이 사라져도, 계속 남아도 둘 다 나쁘다 |

### 3.4 뒤로가기 계약

`graniteEvent.addEventListener('backEvent')` 를 등록하는 순간 **플랫폼 기본 뒤로가기가 차단된다** `[전례]`. 등록했으면 이동과 종료를 전부 우리가 처리한다.

| 지금 자리 | 뒤로가기 결과 |
| --- | --- |
| 시트·모달이 열려 있음 | 그 오버레이만 닫는다 |
| S2 답변 (pending 포함) | S1 홈 |
| S3 · S4 탭 | S1 홈 |
| S5~S9 | 바로 앞 화면 |
| S1 홈 | **미니앱 종료** ("최초 화면에서 뒤로가기를 누르면 미니앱이 종료돼요" `[공식]`) |

> ⚠ `[전례]` **잠금은 등록을 푸는 것이 아니다.** 저장·전송 중에 시트를 못 닫게 하려고 리스너 등록 자체를 풀면 오버레이 스택이 비어서 시스템 뒤로가기가 시트를 건너뛰고 **미니앱을 통째로 닫는다.** 등록은 유지하고 콜백만 삼킨다(`locked` 인자).

### S1 홈 · 고민 입력 `/`

| 항목 | 내용 |
| --- | --- |
| 목적 | "여기에 정말 내 이야기를 적어도 되겠다" 고 느끼게 한다 (PRD 32절 화면 A) |
| 들어오는 길 | 앱 첫 진입 · 탭바 · S2 뒤로가기 · S9 랜딩 CTA · O5 소진 시트 닫기 |

| 로딩 | 없음. 서버 조회를 기다리지 않고 즉시 그린다. 남은 횟수는 나중에 채워지고, **못 읽어도 입력과 전송을 막지 않는다** `[전례: 읽기 실패가 쓰기 진입점을 지우면 앱이 멈춘다]` |
| 오류 | 전송 실패는 입력창 아래 인라인 한 줄 + [다시 해보기]. **입력 내용은 그대로 둔다** |
| 상단바 | 본문에 제목을 그리지 않는다. 서비스 한 줄이 그 역할 |

### O8 간직 완료 피드백 (토스트)

### G1 오프라인 배너

`Environment.getNetworkStatus()` 가 `OFFLINE` `[SDK]`. 화면 최상단에 얇은 줄. 「인터넷이 끊겼어요. 연결되면 이어서 할 수 있어요」. **입력과 초안 저장은 계속 된다.**

### G2 화면 단위 오류 바운더리

> `[전례]` 바깥 바운더리 하나만 두면 화면 하나 때문에 앱이 통째로 크래시 화면이 되고, **거기서는 홈으로 돌아갈 방법이 없다.**

화면마다 바운더리를 둬서 **탭바와 뒤로가기를 살려 둔다.**

### G3 청크 로딩 실패 안내

> `[전례]` lazy 라우트의 `import()` 가 실패하면 실패로 굳어서, 같은 컴포넌트를 다시 그려도 같은 실패가 **즉시** 돌아온다. [다시 시도] 가 영구히 무력해진다.

청크 실패만 가려내서 그때는 다시 그리지 말고 **문서를 새로 받는다.** 버튼 라벨도 「다시 해보기」가 아니라 「새로 고치기」.

## 5. 답변 화면 스크롤 구조 (승부처)

### 5.1 문제 정의

Deep 답변은 2,500자다. 7블록이 한 화면에 안 들어간다. 세 가지를 동시에 만족해야 한다.

1. 스크롤 0 에서 "내 얘기를 읽었다" 가 증명될 것
2. 끝까지 읽게 만들 것 (Answer Completion Rate 가 PRD 31절 가설의 핵심)
3. 다 읽은 사람만 공유·저장으로 보낼 것

### 5.4 스크롤 진행 표시

**넣는다. 단 2px 얇은 선 하나다.**

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 형태 | 본문 최상단 sticky, 높이 2px, 세이지색 | "장식적인 효과나 이펙트는 사용하지 마세요" `[공식]`. 2px 선은 장식이 아니라 진행 정보다 |
| 계산 | 문서 스크롤 비율 | 여기서는 사람 눈에 보이는 값이라 퍼센트로 충분하다. 로그 판정만 블록 기준(D12) |
| 기각 | 「3 / 7」 블록 카운터 | 읽을 게 7개나 남았다는 인상을 준다. 이탈을 만든다 |

### 5.5 「80% 읽음」 측정

| 항목 | 방법 |
| --- | --- |
| 판정 기준 | **⑦ 마지막 한마디 블록이 뷰포트에 10% 이상 들어오고, 그 상태로 2초 이상 머물 때** 한 번 쏜다 |
| 구현 | `IntersectionObserver` + `{threshold: 0.1}` → `Analytics.impression({item_id})`. 앱인토스 공식 로깅 문서의 노출 이벤트 예시와 같은 패턴 `[공식]` |
| 왜 2초인가 | Basic 답변은 짧아서 한 화면에 ⑦ 까지 들어올 수 있다. 그러면 읽지 않아도 완독이 된다. 2초 체류를 붙여 막는다 |
| 기각한 방법 | `scrollTop / scrollHeight >= 0.8`. 큰 폰에서는 완독, 작은 폰에서는 미완독이 되어 기기 간 비교가 안 된다 (D12) |
| 함께 남기는 값 | `mode`(basic·deep) · `last_block`(1~7, 블록마다 도달 로그) · `answer_chars_bucket`(길이 구간) |
| 왜 블록마다 남기나 | 완독률이 낮을 때 **어디서 멈췄는지**를 알아야 고칠 수 있다. ⑤ 에서 끊기면 글이 긴 것이고, ③ 에서 끊기면 경전이 낯선 것이다 |

### 5.6 공유·간직 버튼의 자리

| 자리 | 언제 | 무엇 |
| --- | --- | --- |
| 문서 흐름 (⑦ 아래) | 항상 | [🔗 공유하기] [⭐ 간직하기] 나란히 |
| 하단 고정 바 | **⑦ 도달 후에만** 아래에서 슬라이드 업 | 같은 버튼 둘 |
| 상단 기능 버튼 | **쓰지 않는다** | "미니앱 기능 버튼은 최대 1개" `[공식]`. 읽기 전부터 유료 유도로 보인다 |

하단 바가 광고를 덮을 걱정이 없다: **S2 에는 배너가 없다**(4절).

### 5.7 답변이 도착하는 방식

| 방식 | 채택 | 이유 |
| --- | --- | --- |
| 통째로 한 번에 | ✅ MVP | 블록이 하나씩 나타나면 사용자가 읽는 중에 화면이 밀린다. 그리고 ⑤ 가 늦게 오면 "핵심이 안 왔다" 로 느낀다 |
| 블록 스트리밍 | ❌ | 위 이유. 다만 대기가 20초를 넘는 것이 실측되면 P1 로 재검토 |

## 6. 고민 입력 화면 디테일

### 6.1 키보드가 올라온 상태가 기본

| 항목 | 결정 | 근거 · 주의 |
| --- | --- | --- |
| 진입 시 포커스 | 입력창에 `autofocus` | PRD 3절 "최대한 바로 고민을 쓰게 한다" |
| ⚠ 위험 | iOS WKWebView 는 사용자 제스처 없는 `focus()` 로 키보드를 안 올리는 경우가 있다 `[미확인]` | 안 올라가면 입력창을 크게 잡아 **탭 한 번**으로 올라가게 한다. 실기기 확인 항목 |
| 레이아웃 | `window.visualViewport` 로 입력 묶음 전체를 키보드 위로 올린다 | 인디케이터 줄과 전송 버튼이 키보드 바로 위에 붙어야 한다 |
| 이것은 다크패턴인가 | 아니다 | 금지된 것은 **전면을 가로막는 바텀시트**다. 키보드는 사용자가 하려던 일 자체다 |

│                                     │
│ 무슨 일이 있었나요?                   │  28px
│ 편하게 이야기해 주세요                │
│                                     │
│ ┌─────────────────────────────────┐ │
│ │                                 │ │  멀티라인, 자동 높이
│ │ 오늘 회사에서 ...                │ │  최소 5줄 · 최대 12줄 뒤 내부 스크롤
│ │                                 │ │
│ └─────────────────────────────────┘ │
│ ● ● ○  거의 다 왔어요, 한두 줄만 더요 │  ← 인디케이터 줄
│ 이름·연락처 같은 정보는 적지 않아도    │  ← 개인정보 한 줄 (11px, 보조색)

│                                     │

### 6.3 인디케이터

| 항목 | 결정 | 이유 |
| --- | --- | --- |
| 자리 | 입력창 **바로 아래 왼쪽** | 커서가 입력창 아래쪽에 있어 시선이 가장 가깝다. 입력창 위는 키보드가 올라오면 가장 좁은 자리다 |
| 형태 | `● ○ ○` 점 3개 + 라벨 한 줄 | PRD 3절 그대로 |
| 승급 시점 | 서버 기준과 같은 판정을 **클라이언트에서 동일 로직으로** 계산 | PRD 4절: 120자 이상 **또는** 의미 있는 문장 3개 이상 |
| ⚠ 어긋남 위험 | 클라이언트가 3단계를 보여줬는데 서버가 Basic 으로 처리하면 신뢰가 깨진다 | 판정 규칙을 한 파일로 공유한다. 복잡도 승급(PRD 4절)은 **서버만 위로 올릴 수 있고, 아래로 내리지 못한다** |
| 3단계 도달 | 점 3개가 차고, 라벨이 바뀌고, **점 색이 세이지 → 금색** 으로 한 번 바뀐다 | 보상 순간을 한 번 만든다. 반복 애니메이션은 안 넣는다 (1.2절 그래픽 규칙) |

### 6.4 글자수 표시

| 상태 | 표시 |
| --- | --- |
| 0 ~ 899자 | **숫자 없음.** 점 3개와 라벨만 (D11) |
| 900 ~ 1,000자 | 인디케이터 줄 오른쪽에 `912 / 1,000` |
| 1,000자 도달 | 「1,000자까지 쓸 수 있어요」 + 더 입력되지 않음 |

### 6.5 플레이스홀더 3안

| 안 | 문구 | 평가 |
| --- | --- | --- |
| A | `예) 요즘 자꾸 남들과 비교하게 돼요...` | 예시를 주지만 「예)」 가 폼처럼 보인다 |
| B | `오늘 있었던 일, 요즘 드는 생각, 무엇이든 좋아요` | ✅ **채택.** 무엇을 써도 된다는 허락이 먼저다. 범위를 좁히지 않는다 |
| C | `어떤 마음이 드는지 적어 주세요` | 「마음」 으로 좁혀서, 사건을 쓰려던 사람이 머뭇거린다 |

### 6.6 개인정보 안내 문구

| 항목 | 결정 |
| --- | --- |
| 자리 | 인디케이터 줄 **바로 아래 한 줄, 상시 노출** |
| 왜 툴팁이 아닌가 | PRD 29절이 "첫 화면이나 입력창에 짧게" 라고 명시. 숨기면 그 지시를 어긴다 |
| 문구 | 「이름·연락처 같은 정보는 적지 않아도 괜찮아요」 |
| ⚠ 줄바꿈 | 가운뎃점(`·`)은 `word-break: keep-all` 을 켜도 줄바꿈 자리다 `[전례]`. 「이름·연락처」를 `white-space: nowrap` 으로 묶는다 |
| 실제 방어 | 문구가 아니라 **코드**가 막는다. 전송 직전 전화번호·이메일·주민번호·계좌번호 패턴을 치환한다 `[전례: 값을 화면에 못 오게 하는 것이 문구 규칙보다 세다]` |
| 마스킹 알림 | 전송을 막지 않는다. 답변 화면 상단에 조용히 한 줄: 「연락처처럼 보이는 부분은 빼고 전달했어요」 |

### 6.7 전송 버튼 상태

| 입력 | 버튼 | 라벨 |
| --- | --- | --- |
| 0자 | 비활성 (누를 수 없음) | 이야기 보내기 |
| 1 ~ 119자 | 활성 | 이야기 보내기 |
| 120자 이상 또는 문장 3개 | 활성 | **이야기 보내기** (그대로, D10) |
| 전송 중 | 로딩, 비활성 | 보내는 중 |
| 오늘 3회 소진 | 활성 | 이야기 보내기 → 누르면 O5 시트 |

> 3회를 다 썼다고 버튼을 비활성으로 두지 않는다. 비활성 버튼은 이유를 말해 주지 않는다. 눌러서 시트로 안내한다.

### 6.8 예시 칩

| 항목 | 결정 |
| --- | --- |
| 언제 | 입력창이 **비어 있을 때만**. 한 글자라도 치면 사라진다 |

## 7. 카피 전문

모든 문구는 해요체다(C12). PRD 에 있던 문구는 **원문 / 채택 / 고친 이유**를 함께 적는다.

### 7.1 S1 홈

| 자리 | 문구 | PRD 원문과의 차이 |
| --- | --- | --- |
| 서비스 한 줄 | `부처의 말 · AI 가 경전을 찾아 풀어 드려요` | **신설.** AI 가 답한다는 사실을 첫 줄에서 밝힌다 |
| 제목 | `무슨 일이 있었나요?` | PRD 3절 그대로 |
| 제목 2줄 | `편하게 이야기해 주세요` | PRD 3절. 띄어쓰기만 고침 |
| 보조 문구 | `자세히 이야기할수록 더 깊이 풀어 드릴 수 있어요` | PRD 3절 "더 깊은 답을 드릴 수 있어요" → 「답을 드리다」보다 「풀어 드리다」가 이 제품이 하는 일에 가깝다 |
| 플레이스홀더 | `오늘 있었던 일, 요즘 드는 생각, 무엇이든 좋아요` | 신설 (6.5절 B안) |
| 개인정보 | `이름·연락처 같은 정보는 적지 않아도 괜찮아요` | PRD 29절을 한 줄로 줄임. 「가급적 적지 말아주세요」는 금지형이라 「적지 않아도 괜찮아요」로 |
| 전송 버튼 | `이야기 보내기` | 신설 (D10) |
| 남은 횟수 | `오늘 2번 더 이야기할 수 있어요` | 신설. 「무료 3회 중 1회 사용」 같은 명사 나열을 피한다 |
| 복귀 카드 | `방금 물어본 이야기의 답이 준비됐어요` + `[답 보러 가기]` | 신설 (D3) |
| 초안 복구 | `이어서 쓸 수 있게 남겨 뒀어요` + `[지우기]` | 신설 |
| 마스킹 알림 | `연락처처럼 보이는 부분은 빼고 전달했어요` | 신설 |

**인디케이터 라벨 3안씩** (굵은 것이 채택):

| 단계 | 안 1 | 안 2 | 안 3 |
| --- | --- | --- | --- |
| `● ○ ○` | 조금만 더 이야기해 주세요 | **조금 더 들려주면 더 잘 풀어 드릴 수 있어요** | 세 줄 이상 쓰면 깊은 풀이를 받을 수 있어요 |
| `● ● ○` | 조금만 더요 | **거의 다 왔어요, 한두 줄만 더요** | 한 줄만 더 쓰면 깊은 풀이예요 |
| `● ● ●` | 깊은 풀이 준비 완료 | 이제 깊은 풀이를 받을 수 있어요 | **✨ 이 정도면 깊이 풀어 드릴 수 있어요** |

고른 이유:
- 1단계 안 2 채택: 안 1(PRD 3절)은 **부탁**이라 부담을 준다. 안 3은 「세 줄 이상」이라는 **조건**이라 과제가 된다. 안 2는 내가 무엇을 얻는지를 말한다.
- 2단계 안 2 채택: 「거의 다 왔어요」가 진행을 알리고, 「한두 줄만」이 남은 양을 작게 보이게 한다. 안 3의 「한 줄만 더 쓰면」은 실제와 어긋날 수 있다(문장 수 기준이면 한 줄로 안 될 수 있다).
- 3단계 안 3 채택: PRD 원문 「깊은 풀이 준비 완료」는 **명사+명사**라 토스 라이팅 규칙 위반이다. 안 2는 밋밋하다. 안 3은 「이 정도면」으로 **사용자가 한 일을 인정**한다.

### 7.2 S2 답변 · 생성 중

## 9. 이벤트 로깅 매핑

### 9.1 수집 경로

토스 공식 `Analytics` 하나만 쓴다. 자체 이벤트 테이블도 외부 분석 도구도 만들지 않는다 `[전례 ADR-0019]`.

- 이유: 경로가 둘이면 "무엇이 어디에 남는가" 에 답할 수 없다. 고민을 다루는 앱이라 그 답이 필요하다.
- 분석용 사용자 id·발생 시각·서버 수신 시각은 **SDK 가 이미 붙인다.** 우리가 만들면 익명키를 로그에 직접 싣게 된다.
- 대가: 질의가 콘솔이 주는 만큼으로 묶인다.

`kind` 는 네 가지다 `[전례 실측]`: `screen` · `click` · `impression` · `event`.
공식 문서가 주는 것은 `Analytics.click({button_name})` 과 `Analytics.impression({item_id})` 다 `[공식]`.

### 9.2 이벤트 표

| 이벤트 | kind | 어느 화면 | 어느 동작 | 파라미터 |
| --- | --- | --- | --- | --- |
| `app_open` | event | 전역 | 앱 실행. 세션당 1회 | `is_first_open` · `days_since_first_open` · `days_since_last_open` · `open_bucket` · `entry`(home·share·deeplink) |

| `concern_seed_tap` | click | S1 | 예시 칩 탭 | `seed_id`(anxiety·anger·choice) |
| `draft_restored` | event | S1 | 초안 복구됨 | `age_hours_bucket` |
| `deep_threshold_reached` | event | S1 | 3단계 도달 | `reason`(length·sentences) |
| `concern_submit` | click | S1 | 전송 | `mode_expected`(basic·deep) · `len_bucket` · `masked`(마스킹 했나) |
| `quota_exhausted` | event | S1 → O5 | 3회 소진 상태에서 전송 | `remaining`(0) |

### 9.3 절대 싣지 않는 값

`[전례]` 를 그대로 따른다.

| 안 싣는 것 | 왜 |
| --- | --- |
| 고민 원문, 그 일부, 글자 수의 **정확한 값** | 원문은 물론이고 길이도 구간(`len_bucket`)까지만 |
| 답변 원문, 경전 원문, 마지막 한마디 | 공유 카드에 나가는 문장이라도 로그에는 안 넣는다 |
| 자유 텍스트 감정 태그 | **고정 코드 10종**(`anxiety`·`comparison`·`anger`…)만. LLM 이 만든 새 태그는 `other` |
| 기기 ID, 익명키 | `Environment.deviceId` 는 S6 화면에만 보여준다 `[전례]` |
| 예외 메시지 본문과 스택 | 화면이 죽는 자리는 대개 방금 넣은 값을 다루던 자리라 메시지에 그 값이 실려 있다 `[전례]` |
| 실행 횟수의 정확한 값 | 구간(`open_bucket`)으로. 217번 연 사람은 한 명이다 `[전례]` |

### 9.4 PRD 30절 핵심 지표 계산식

| 지표 | 계산 | 낮으면 볼 것 |
| --- | --- | --- |
| Deep Conversion Rate | `deep_threshold_reached` 사용자 ÷ `concern_input_start` 사용자 | 인디케이터 문구, 예시 칩의 길이 |
| Answer Completion Rate | `answer_scroll_complete` ÷ `answer_generated`, **mode 별로 나눠서** | `answer_block_view` 의 `block` 분포로 어디서 멈췄는지 본다 |
| Share Rate | `share_complete` ÷ `answer_generated` | 미리보기 안심 문구, 카드 디자인 |
| Save Intent Rate | `save_click` ÷ `answer_generated` | Premium 구매 의향 선행 지표 |
| 대기 이탈 | `answer_generated` ÷ `concern_submit` | 대기 시간, 순차 문구 |

> ⚠ **모드를 나누지 않은 완독률은 의미가 없다.** Basic 은 짧아서 완독이 쉽다. 나누지 않으면 Basic 비중이 올라갈 때 완독률이 저절로 좋아진 것처럼 보인다.

> ⚠ 토스 SDK 는 **운영 판에서만 실제로 보내고 그 밖에서는 조용히 삼킨다** `[전례]`. 개발·e2e 에서 "무엇이 찍혔나" 를 보려면 운영이 아닐 때만 `window.__logs` 에 사본을 쌓는 래퍼가 필요하다.

> ⚠ **로그가 답변을 막지 않는다.** 브릿지 실패는 삼키고 재전송 대기열을 두지 않는다 `[전례]`.

### 9.5 콘솔 핵심 지표 설정

앱인토스 콘솔은 활성 지표 1개, 전환 지표 최대 3개를 받는다 `[공식]`. 이 값으로 토스가 **비슷한 사용자에게 우리 앱을 노출·추천**한다.

| 자리 | 제안 | 이유 |
| --- | --- | --- |
| 활성 지표 | `answer_generated` 가 있는 사용자 | 앱을 열기만 한 사람과 실제로 답을 받은 사람을 가른다 |
| 전환 1 | `answer_scroll_complete` (mode=deep) | PRD 31절 성공 가설과 정확히 같다 |
| 전환 2 | `share_complete` | 성장 루프의 입구 |
| 전환 3 | `save_click` | Premium 선행 지표 |

## 10. PRD 와 어긋나는 지점

| # | PRD 절 | 어긋남 | 제안 |
| --- | --- | --- | --- |
| P1 | 17절 (광고 위치 1) | 「다른 고민 이야기하기」 → 전면 광고는 **"예상하지 못한 순간에 광고가 노출되는 경우"** 에 해당할 수 있다. 출시 불가 사유다 `[공식]` | MVP 에서 전면 광고를 뺀다(D7). P1 로 붙일 때는 버튼 라벨에 광고를 명시하고, 사전 로딩 규칙을 지킨다 |
| P2 | 24절 (공유 Growth Loop) | "친구가 공유 이미지·링크 클릭 → 공유된 말씀" 이 웹에서 열리는 것처럼 읽힌다. 실제로는 `intoss://` 링크라 **토스 앱이 없으면 스토어로 간다** `[공식]` | ① 링크 미리보기(OG 이미지)가 토스 밖에서 읽히는 유일한 콘텐츠임을 전제로 **카드 이미지에 핵심 문장을 크게 넣는다** ② 웹 랜딩이 필요하면 별도 웹페이지를 우리가 운영해야 하는데, "자사 사이트로 이동 금지" 조항과 충돌하므로 **미니앱 밖 유입은 P2 로 미룬다** |
| P3 | 28절 (LLM 출력 구조) | `personalAnalysis: string` 하나로는 ⑤ 블록을 소제목 3개로 못 쪼갠다. 2,500자를 한 덩어리로 주면 읽다 만다 | `personalAnalysis: { heading: string, body: string }[]` (2~3개). Basic 은 1개도 허용 |
| P4 | 28절 | `actions: string[]` 만으로는 ⑥ 을 못 그린다. 각 행동에 "왜" 가 붙어야 하루를 바꾼다 | `actions: { title: string, why?: string }[]` |

## 12. 시안을 만들 때 먼저 볼 것

1. **5.2절 답변 화면 세로 구조**가 이 제품의 전부다. 여기부터 그린다.
2. **6.2절 입력 화면 배치**를 키보드가 올라온 상태로 그린다. 내려간 상태는 부수적이다.
3. 상단바를 그리지 않는다(C1). 화면 제목은 본문 첫 줄이다(C2).
4. 다크 테마를 만들지 않는다(C11).
5. 배너 자리는 **가로 100% · 높이 96px** 고정, 안은 비워 둔다 `[공식]`. 개발용 목은 60/120px 이라 **레이아웃 수치를 목으로 검증하면 안 된다** `[전례]`.
6. 시안에 쓴 색·크기를 그대로 토큰으로 뽑는다. `[전례]` PRD 가 토큰 9개만 정의했는데 시안이 30개를 쓴 적이 있다. 카드 흰색이 배경 위에 얹히는 2층 구조를 PRD 만 보고 만들면 대비가 사라진다.
7. 안내 문구에는 `word-break: keep-all` 을 기본으로 켜고, 가운뎃점으로 묶인 말은 `nowrap` 으로 감싼다 `[전례]`.
