### 1-2. 핵심 법리 한 줄

**원문이 퍼블릭 도메인이어도 번역은 별개 저작물이다.** 한국 저작권법상 번역은 2차적저작물로 독자적으로 보호되고, 보호기간은 저작자 사후 70년이다. 그래서 "법구경은 2,500년 됐으니 아무거나 써도 된다"는 틀렸다. 실제로 막히는 것은 번역이다.

CC0 는 이 문제를 통째로 없앤다. 저작권자가 권리 자체를 포기했으므로 우리가 그 위에 만든 한국어 번역은 **우리 저작물**이 된다(2차적저작물 이용 허락을 받는 구조가 아니다).

### 1-3. 결정: 「CC0 영역 → 우리 한글 번역 → 사람 감수」 경로

```
bilara-data (CC0, 커밋 SHA 고정)
  ├─ root/pli/ms/...   팔리 원문     ← 감수자 대조용. 화면에는 미노출(D3)
  └─ translation/en/sujato/...  영역  ← 번역 기준본
          ↓  LLM 초벌 번역 (빌드 타임, 런타임 아님)
       한국어 초벌
          ↓  사람 감수 (필수 게이트)
       ko.text  ← 우리 저작물, 화면에 나가는 유일한 경전 문자열
```

**이 경로를 고른 이유**

- 원문 확보 비용이 0 이다. 라이선스 협상·이용 허락 대기가 없다.
- 세그먼트 단위로 팔리와 영역이 정렬돼 있다(`dhp1:1` 형태). 감수자가 원문 대조를 할 수 있고, 출처 표기가 자동으로 정확해진다.
- 법구경 423게가 전부 있다. MVP 300구절을 법구경 하나로도 채울 수 있다.

**기각한 대안**

| 대안 | 기각 이유 |
|---|---|
| Access to Insight 영역본을 쓴다 | CC BY-NC. 광고 붙는 순간 위반이다 |
| 동국역경원 한글대장경을 크롤링해 쓴다 | 이용 조건 미확인 + 기관 저작물 무단 이용 리스크. **「명시적으로 금지 안 됨」은 근거가 못 된다**(10초 가계부 교훈, 광고 X버튼 건) |
| 1929년 이전 PD 영역본에서 옮긴다 | 라이선스는 깨끗하지만 문체가 낡아 오히려 번역 품질이 떨어진다. 굳이 CC0 현대 영역본을 두고 갈 이유가 없다 |
| 한글 번역본 출판사에 이용 허락을 받는다 | 가능은 하다. 다만 MVP 일정 안에 협상이 끝난다는 보장이 없고, 권당 로열티가 붙으면 무료 사용자 모델과 충돌한다. **플랜 B 로만 남긴다** |

#### 3-1-1. 실제 시드가 들고 있는 필드 (2026-09-15)

위 표는 **원안**이다. 실제로 만들어진 `data/scriptures/seed.json`(399구절)은 모양이 다르다. 여기가 정본이고, 값을 만드는 곳은 `tools/build_scripture_seed.py` 하나다(감수본 마크다운 → 시드). 손으로 고치지 않는다.

**들어온 것 중 원안에 없던 것이 화자·귀속이다.** 「불교 문헌의 문장」과 「부처가 직접 한 말」이 다르다는 것을 데이터가 들고 있어야 했다. 법구경은 전승상 부처의 가르침이지만 어느 자리에서 한 말인지 화자가 특정되지 않고, 테리가타·승만경·선어록은 아예 다른 사람이 말한다. 서비스 이름이 「부처의 말」이어도 화자를 부처로 바꾸지 않는다. 실제로 감수 통과 16구절 중 **부처의 직접 발언은 둘뿐이다**(an.2.33 · sn.1.34). 여덟은 화자가 특정되지 않은 법구경(`canonical_tradition`)이고, 나머지 여섯은 원효 · 법화경의 제자들 · 오조 홍인 · 승만부인 · 뿐니까 장로니 · 조주 선사의 말이다.

### 3-3. `retrieval_text` 가 따로 있는 이유 (중요)

게송 원문으로 검색하면 안 된다. 「수레가 소의 발자국을 따르듯이」와 「회사 상사가 나한테만 뭐라고 해요」는 어떤 검색 방식으로도 안 붙는다. 게송은 은유이고 고민은 서술이라 어휘가 겹치지 않는다.

그래서 **구절마다 「이 구절이 닿는 상황」을 평서문으로 써 둔다.** 이게 실제 검색 대상이다. 나중에 임베딩을 켤 때도 임베딩 대상은 `retrieval_text` 이지 `ko.text` 가 아니다.

`retrieval_text` 는 감수 대상에 포함한다. 여기가 틀리면 아무리 좋은 구절도 엉뚱한 고민에 붙는다.

## 4. MVP 큐레이션 규모: 초안 400, 출시 하한 200

### 4-1. 산식

```
반복 방지 쿨다운 창 = 최근 10회 노출 구절 제외
→ 태그당 후보가 10개면 11번째에 후보가 0이 된다
→ 태그당 최소 12개 (쿨다운 10 + 여유 2)
→ 품질 목표는 태그당 20개 (LLM 재순위에 줄 후보 5개를 다양하게 뽑으려면)

10종 × 20 = 200 (태그 배정 기준)
구절 하나가 평균 1.6개 태그를 가지므로
유니크 구절 ≈ 200 × 10 / 1.6 / 10 ... 정확히는 200 / 1.6 = 125 가 최소 유니크

여기에 난이도 분산(easy/normal/deep)과 경전 출처 다양성을 얹으면
실무 목표 300, 하한 200, 상한 400
```

| 대승·선·한국 불교 | 50 | | 금강경·반야심경·유마경·법화경·육조단경·원효·지눌·서산·선어록. **라이선스 확인 대상** |
| **합계 (초안)** | **400** | | |
| **출시 하한 (감수 통과)** | **200** | | 4-1 산식의 최소 유니크 125 를 넘는다 |

⚠ **2026-09-15 개정.** 300구절 안이 X6 에서 「법구경만 120」으로 줄었다가 **초안 400 · 출시 하한 200**
으로 다시 잡혔다. 줄였던 이유(감수 병목)는 그대로 살아 있다. 달라진 것은 **초안을 AI 가 쓴다**는
점이다. 초안 생성 비용은 구절 수에 거의 비례하지 않으므로 400 을 한 번에 만들어 두고,
사람이 감수를 통과시킨 만큼만 빌드에 싣는다. 감수는 하루 3시간 기준으로 200구절에 7~8일,
400구절 전부면 11~22일이 든다. **출시를 감수 완료에 묶지 않는다.**

법구경 한 권만으로는 어조가 반복되고 감정 태그 열 종을 고르게 못 채운다는 것이 규모를 다시
올린 이유다. 태그 하나에 최소 12구절(쿨다운 10 + 여유 2)이 있어야 같은 구절이 반복되지 않는데,
초안 200구절 시점에 `comparison`·`money`·`apathy` 가 하한에 못 미쳤다.

⚠ **대승 문헌 25구절은 라이선스 상태가 다르다.** 팔리 문헌은 CC0 영역본(Sujato)을 기준본으로 삼을 수 있지만 대승은 그런 기준본이 없다. 한문 원전 자체에는 저작권이 없으나 어느 판본에서 옮겼는지가 확인 대상이고, 한글은 동국역경원 판본 문제가 걸린다. 아함경은 한역 기반이라 CBETA 이용 조건 확인이 먼저다.

그래서 **초안에는 넣되 `license_status: needs_check` 를 박고, 감수 통과 조건에 「기준 판본 확정」을 더한다.** 라이선스가 정리되지 않으면 그 25구절은 빌드에서 빠지고 팔리 175구절로 출시한다. 175 는 4-1 산식의 최소 유니크 125 를 넘으므로 출시가 막히지는 않는다.

### 4-3. 구절당 필드 충족 기준 (감수 통과선)

- [ ] `ko.text` 번역이 `base_translation` 과 뜻이 어긋나지 않는다

- [ ] `cautions` 를 한 번은 생각해 봤다 (없으면 「없음」이라고 명시적으로 적는다. 빈 배열을 방치하지 않는다)

## 5. 검색 방식: 태그 + 규칙 점수 + LLM 재순위

### 5-1. 세 방식 비교

| | 태그 기반 | 벡터 임베딩 | 하이브리드(태그 → 임베딩 재순위) |
|---|---|---|---|
| 커버리지 보증 | ✅ 태그당 최소 개수를 빌드가 강제 | ❌ 보증 불가 | ✅ |
| 엉뚱한 구절 위험 | 중 (태그 안에서 결이 안 맞을 수 있음) | **높음** (은유와 서술이 안 붙는다) | 중 |
| 추가 API 호출 | 0 | 쿼리 임베딩 1회 (+50~150ms) | 1회 |
| 재현성·회귀 테스트 | ✅ 결정론적 | 중 | 중 |
| 운영 복잡도 | 낮음 | 인덱싱 파이프라인 + 모델 버전 고정 필요 | 높음 |
| 300구절에서의 이득 | 기준 | 태그 필터 후보가 12~20개뿐이라 **줄일 것이 없다** | 이득 거의 없음 |
| 3,000구절에서의 이득 | 후보가 100+ 로 불어남 | 필요해짐 | ✅ 필요 |

### 5-2. 결정: MVP 는 임베딩을 쓰지 않는다

> **2026-09-15 뒤집힘. 임베딩을 켰다.** 아래 원안은 기록으로 남긴다.
>
> 원안의 근거는 「태그 필터를 지나면 후보가 12~20개라 코사인이 이길 자리가 없다」와
> 「골든셋이 없어 좋아졌는지 못 잰다」 둘이었다. 시드가 120구절에서 400구절로 늘면서 첫 근거가
> 깨졌고(테마 하나에 110구절이 붙는다), 둘째 근거는 골든셋을 만들어서 없앴다.
>
> **먼저 자를 만들었다.** 고민 글 26개에 맞는 구절을 사람이 판정해 골든셋 135쌍을 만들었다
> (`tools/eval/`). 한쪽 방식에 유리하지 않도록 어휘 상위 10과 벡터 상위 10을 합친 풀에서
> 골랐다(pooled judgment). 그다음 같은 자로 세 방식을 쟀다.
>
> | 방식 | Recall@5 | Recall@20 | MRR |
> | --- | --- | --- | --- |
> | 어휘만 (원안) | 0.390 | 0.623 | 0.688 |
> | 벡터만 | 0.287 | 0.578 | 0.618 |
> | 어휘 + 벡터 (RRF 2:1) | **0.410** | **0.691** | **0.860** |
>
> **벡터 혼자로는 어휘를 못 이긴다.** 그런데 합치면 둘 다 넘는다. 서로 다른 것을 놓치기
> 때문이다. 어휘는 낱말이 겹쳐야 잡고, 벡터는 뜻이 닿으면 잡는다. 고민 글은 사건을 쓰고
> (구조조정 · 월세 · 대출) `retrieval_text` 는 마음 상태를 써서(불안 · 최악을 상상) 낱말이
> 만나지 않는 짝이 많다. 그 자리를 벡터가 메운다.
>
> **값은 결정 요인이 아니었다.** 구절 400개를 미리 임베딩하는 데 한 번 $0.0006, 요청마다 드는
> 쿼리 임베딩은 $0.000002다. 답변 한 건 값이 $0.0035이므로 0.06%다. 원안이 걱정한 운영 비용은
> 실제로 재 보니 없었다.
>
> **지연도 늘지 않았다.** 쿼리 임베딩 0.4~0.8초를 분류 호출과 **병렬로** 돌린다. 분류가 1초
> 넘게 걸리므로 그 안에 끝난다. rules 가 위기·잘못된 입력으로 확정하면 그 앞에서 돌아가므로
> 위기 글은 임베딩에도 가지 않는다.
>
> 켠 방식은 5-3 표와 다르다. 표는 「태그 → 임베딩 재순위」였는데, 1차 패스가 테마를 정하는
> 단계라 그 시점에는 테마가 없다. 그래서 테마 없이 400구절 전체에 두 순위를 매겨 RRF 로 합친다.
> 임베딩 대상은 표대로 `retrieval_text` 를 쓰되 `modern_gloss` 와 본문을 덧붙인 것이 가장
> 좋았다(상황만 쓰면 R@20 0.698 → 0.666).
>
> 남은 한계: 골든셋 135쌍은 사람 한 명이 판정한 것이고 26개 고민이 모든 상황을 덮지 않는다.
> 감수를 하면서 `retrieval_text` 가 좋아지면 다시 재야 한다. 자는 `tools/eval/measure.py` 다.

### 5-2-1. 결정: 후보 풀을 환경으로 가른다 (2026-09-15)

사용자 지시는 「production 에는 approved 만」이었는데 구현이 local·dev 까지 묶어 **모든
환경에서 감수 통과 16구절**로 돌았다. 검수에서 그 판이 무너졌다. 화면은 경전 자리에
「이 고민과 닿아 있는 실제 가르침」이라고 먼저 약속하는데, 16구절로는 그 약속을 지킬 수 없다.

- 팀에서 겉도는 고민에 「개구리와 거북이도 하늘에 가야 할 것」이 세 번 중 두 번
- 엄마를 잃고 자책하는 사람에게 「젊어서 닦지 않은 사람은 탄식한다」가 다섯 번 전부
- 이별과 카드값에 똑같이 「모든 법은 자아가 아니다」

같은 자(골든셋 26고민 · 135쌍)로 두 풀을 재 보면 이유가 한눈에 보인다. 실제 `candidates()`
경로를 그대로 돌린 값이다.

| 후보 풀 | Recall@5 | Recall@20 | MRR | 상위 20에 정답이 하나라도 든 고민 |
| --- | --- | --- | --- | --- |
| 399구절 (초안 포함) | **0.390** | **0.684** | **0.827** | **26 / 26** |
| 16구절 (감수 통과분) | 0.039 | 0.047 | 0.158 | 6 / 26 |

**26개 고민 중 20개는 정답 구절이 16구절 안에 아예 없다.** 검색을 아무리 고쳐도 없는 구절은
못 고른다. 감수 16구절에는 anger·approval 테마 구절이 하나도 없어서, 화가 난 고민에 화를
말하는 구절이 애초에 존재하지 않는다.

그래서 이렇게 가른다. 스위치는 `SCRIPTURE_POOL`(`Settings.scripture_pool`) 하나다.

| 값 | local · dev | prod |
| --- | --- | --- |
| `auto` (기본) | 초안 포함 399구절 | 감수 통과분만 |
| `approved` | 감수 통과분만 | 감수 통과분만 |
| `draft` | 초안 포함 399구절 | **기동 실패** |

앞 회차가 16구절로 묶으며 적어 둔 우려 셋을 이렇게 다룬다.

| 우려 | 어떻게 다루나 |
| --- | --- |
| 미감수 문장이 화면에 나간다 | 운영에는 못 나간다. `_guard`(core/config.py)와 `repo._retrieval_pool` 이 두 겹으로 기동을 멈춘다. 나가는 곳은 local·dev 뿐이고, 기동 로그와 `/health` 가 초안이 몇 구절 섞였는지 말한다 |
| 개발과 운영이 다른 구절로 돈다 | `SCRIPTURE_POOL=approved` 한 줄로 개발에서도 운영과 같은 16구절 판을 본다. 배포 날이 아니라 지금 본다 |
| 안전 규칙이 미감수 383구절에 검증된 적 없다 | 스위치로 못 덮는 우려라 규칙 쪽을 고쳤다. **안전 규칙은 감수 여부와 무관하게 399구절 전체에 걸린다.** 실제로 새던 구절이 12건 있었고 근거와 함께 막았다(아래) |

세 번째가 진짜였다. 규칙이 감수본 16구절만 보고 만들어져서 초안 쪽 표현을 못 보고 있었다.

**사별 규칙은 아예 한 번도 돈 적이 없었다.** spec 이 `bereavement` 를 모델 신고 값으로만
두었는데, 검수 사례를 실제 모델에 넣어 보니 「엄마가 돌아가셨는데 장례식에서 울지
못했어요」에 모델이 그 값을 신고하지 않았다. 신고가 없으면 사별 구절 제외가 통째로 죽는다.
그래서 서버도 함께 보게 했다(`safety.BEREAVEMENT`, 결정론 판정). 죽음을 말하는 낱말만
세우므로 「헤어졌어요」 같은 이별은 여기 서지 않는다. 자책 판정도 같은 사례에서 새고 있었다.
「제 탓이에요」만 보고 있어서 「제가 엄마를 사랑하지 않았던 걸까요」를 못 봤다.

이 열넷을 막아도 각 상태에서 후보는 풀의 절반 위로 남는다(가장 많이 빼는 학대가 399 → 356).
**새는 것이 더 있다고 보는 편이 맞다.** 규칙은 계속 넓히고, 기동 게이트
`check_every_flag_bites` 가 풀 모드와 상관없이 시드 399구절로 「깃발마다 실제로 빠지는 구절이
있나」를 잰다.

**남는 것.** 399구절 풀에서도 Recall@20 은 0.684다. 열에 세 번은 닿는 구절을 상위 20에도
못 올린다. 화면이 「이 고민과 닿아 있는」이라고 단정하는 자리를 서버가 늘 뒷받침하지는
못한다는 뜻이다. 서버가 줄 수 있는 신호는 5-2-2 에 적었다.

### 5-2-2. 서버가 줄 수 있는 「닿았나」 신호

화면 문구를 고치는 것은 이 절의 몫이 아니다. 여기서는 **서버가 무엇을 사실로 말할 수 있는지**만
정한다. 셋이 있고, 앞의 둘은 이미 서버가 알고 있다.

| 신호 | 서버가 아는가 | 뜻 | 드는 값 |
| --- | --- | --- | --- |
| 모델이 고른 구절인가, 서버가 대신 고른 것인가 | **이미 안다** (`compose.compose_pass1` 의 whitelist 실패 자리) | 서버 대체는 모델이 후보 밖 id 를 냈거나 안전 규칙에 걸린 자리다. 「닿았다」고 말할 근거가 가장 약하다 | 0 |
| 그 구절이 후보에서 몇 번째였나 | **이미 안다** (`Pending.candidate_ids` 의 자리) | 20번째로 잘린 구절이 뽑혔다면 어휘도 벡터도 그 구절을 밀지 않았다는 뜻이다 | 0 |
| 모델이 스스로 「닿았다」고 판정한 값 | 아직 모른다 | 1차 패스 출력에 `scriptureFit`(`direct` / `loose`) 한 칸을 더해 받는다 | 출력 토큰 몇 개 |

**권하는 길.** 세 번째를 더하고, 셋 중 하나라도 약하면 서버가 `scriptureFit: "loose"` 를 내려
보낸다. 화면은 그때 경전 카드 제목을 단정하지 않는 말로 바꾼다(문구는 다른 갈래 몫).
**경전 자리를 비우는 길은 권하지 않는다.** 답변 스키마가 경전을 최소 하나 요구하고
(`spec/answer.schema.json` scriptures minItems 1), 경전이 빠지면 이 제품이 일반 상담 앱과
같아진다. 약하게 말할 수는 있어도 없앨 자리는 아니다.

이걸 실제로 내보내려면 `spec/answer.schema.json` 과 `integrations/llm/schemas.py` ·
`prompts.py` 를 함께 고쳐야 한다. 셋 다 이 작업의 파일 영역 밖이라 여기서는 정의만 남긴다.
서버 쪽 준비는 해 두었다. `compose.Pending.scripture_source` 가 모델이 골랐는지 서버가
대신 골랐는지를 들고 있고, 요청마다 `scripture_pick` 로그가 그 값과 후보 순위를 남긴다
(고민 글은 싣지 않는다). 실제로 얼마나 자주 서버 대체로 빠지는지는 그 로그로 먼저 본다.

### 5-2-4. 사용자처럼 다시 넣어 본 결과 (2026-09-15, 2차)

앞 회차 값을 믿지 않고 같은 일을 다시 했다. 실제 OpenAI 모델을 붙여 검수 사례 셋을 각

**규칙은 서 있었는데 깃발이 안 서 있었다.** 앞 회차가 구절 쪽(무엇을 뺄까)을 고쳤다면
이번에 크게 샌 곳은 판정 쪽(누구에게서 뺄까)이었다. 사별을 말하는 글 셋이 하나도
`bereavement` 를 세우지 못했다.

| --- | --- | --- |

#### 5-2 원안(기록): 임베딩을 안 쓰기로 했을 때의 파이프라인과 근거

아래 그림과 세 줄은 **5-2 가 뒤집히기 전**에 적어 둔 것이다. 지우지 않고 남겨 두되, 5-2-4 의
결론으로 읽히지 않도록 여기서 한 번 끊는다. 실제로 도는 검색은 5-2 · 5-2-1 이고, 그림 속
`tags.primary` · `difficulty` · `excluded_for` 는 지금 시드에 없는 칸이다(3-1-1절).

```
① LLM 1차 패스 (저가 모델, PRD 5·41절의 Router 와 같은 호출)
   입력: 고민 원문
   출력: emotionTags[1~4], themes[3~5], safetyFlag, complexity, 길이·문장수
         → PRD 4절 Router 입력이 여기서 같이 나온다

② 서버 검색 (LLM 없음, 결정론적)
   a. safetyFlag 가 서면 → 검색 중단, 고정 안내 (6-4절)
   b. tags.primary ∩ emotionTags 로 필터
   c. excluded_for ∩ 고민 컨텍스트 플래그 → 제외
   d. 최근 10회 노출 구절 제외
   e. 점수 = 태그 일치 수 ×3 + themes 문자열 일치 수 ×2
            + (Basic 이고 difficulty=easy 면 +2)
            + 노출 횟수 역가중 (적게 나간 구절 우대)
   f. 상위 5개를 후보로 (Deep 은 5개, Basic 은 3개)

③ LLM 2차 패스 (Basic/Deep 모델, PRD 7~12절 답변 생성)
   입력: 고민 원문 + 후보 5개의 {id, ko.text, citation_ko, modern_gloss, cautions}
   출력: scriptureId (후보 id 중 하나) + 선정 이유 한 줄 + 나머지 답변 필드
   ⚠ scripture 의 text/source/chapter 를 LLM 에게서 받지 않는다

④ 서버 조립
   scriptureId 로 DB 에서 원문·출처를 붙인다
   scriptureId 가 후보 밖이면 → 1순위로 강제 치환 + scripture_fallback 로그
```

**임베딩을 안 쓰는 근거 세 줄**

1. 태그 필터 후보가 12~20개다. 그중 5개를 고르는 일에 코사인 유사도보다 LLM 의 문맥 판단이 낫다. 그리고 그 LLM 호출은 **어차피 답변 생성을 위해 하는 호출**이라 추가 비용이 후보 5개의 요약 토큰(약 800토큰)뿐이다.
2. 골든셋이 없는 상태에서 임베딩을 켜면 좋아졌는지를 못 잰다. 10초 가계부 교훈 「검증 스텁을 만들면 그 스텁만 보고 안심하게 된다」: 스텁으로 잰 정확도를 성능으로 인용하는 사고를 이미 겪었다.
3. 구현·운영이 한 겹 는다. 모델을 바꾸면 **전 구절 재인덱싱**이 필요하고, 인덱싱 모델과 쿼리 모델이 어긋나면 조용히 품질만 떨어진다(에러가 안 난다).

### 5-3. 임베딩을 켜는 조건과 그때의 선택

> **이 절은 이미 지나간 자리다 (2026-09-15).** 아래 트리거 표는 「언제 켤까」를 미리 정해 둔 것인데, 첫 줄(구절 수 1,000개 초과)에 닿기 전에 5-2 가 실측으로 켰다. 400구절에서 테마 하나에 110구절이 붙어 트리거의 전제였던 「후보 12~20개」가 먼저 깨졌기 때문이다. 표는 기록으로 남긴다.
>
> **실제로 켠 것과 표가 다른 자리 셋.** ① 「태그 → 임베딩 재순위」가 아니라 테마 없이 풀 전체에 두 순위를 매겨 RRF(2:1)로 합친다. 1차 패스가 테마를 정하는 단계라 그 시점에 테마가 없다. ② 임베딩 대상은 `retrieval_text` 만이 아니라 `modern_gloss` 와 본문을 덧붙인 것이다(상황만 쓰면 R@20 0.698 → 0.666). ③ 전환 스위치 `RETRIEVAL_MODE` 는 만들지 않았다. 벡터 파일이 없거나 씨앗·모델·차원이 어긋나면 그 사실이 로그에 남고 어휘 검색만으로 이어 간다.
>
> 표에서 그대로 산 것은 **모델과 저장소**다. `text-embedding-3-small` 1536차원, JSON 번들 + 인메모리. 399구절 벡터가 `data/scriptures/embeddings.json` 에 미리 계산돼 있고 런타임에 다시 부르지 않는다. 쿼리 임베딩만 요청마다 한 번 부르는데, **분류 호출과 병렬로** 돌아 화면이 기다리는 시간은 늘지 않는다. rules 가 위기·잘못된 입력으로 확정하면 그 앞에서 돌아가므로 **위기 글은 임베딩에도 가지 않는다.**

| 트리거 | 값 |
|---|---|
| 구절 수 | **1,000개 초과** |
| 또는 태그 필터 후보 | **25개 초과가 상위 3개 태그에서 상시 발생** |
| 또는 태그를 10종에서 20종 이상으로 늘릴 때 | 태그 관리 비용이 임베딩 운영 비용을 넘는 지점 |

켤 때의 선택(지금 정해 두고 코드 인터페이스만 미리 판다):

| 항목 | 1순위 | 예비 | 근거 |
|---|---|---|---|
| 모델 | OpenAI `text-embedding-3-small` | Google `gemini-embedding-001` | 가격 $0.02/1M vs $0.15/1M (2026-09 웹 조사 기준). 고민도 구절도 한국어라 **같은 언어 안 비교**이므로 다국어 우위가 결정적이지 않다 |
| 임베딩 대상 | `retrieval_text` | | `ko.text`(게송)를 임베딩하면 안 붙는다 (3-3절) |
| 저장소 | **JSON 번들 + 인메모리 numpy** | pgvector | 1,000×1536 float32 = 6MB. Cloud Run 512Mi 안. 행렬곱 1ms 미만 |
| 전환 스위치 | `RETRIEVAL_MODE=tag\|hybrid`, `EMBEDDING_PROVIDER`, `EMBEDDING_MODEL` | | 10초 가계부가 `LLM_PROVIDER`·`LLM_MODEL`·`LLM_ESCALATION_MODEL` 세 줄로 갈아탄 전례 그대로 |

⚠ 10초 가계부 교훈 「값은 결정 요인이 아니다 라고 적은 지 사흘 만에 값이 결정 요인이 됐다」: `gemini-2.5-flash` 가 새 키에 404 로 막히고 후속 모델이 2.5배 비싸진 일을 이미 겪었다. **임베딩 모델을 고르는 ADR 에는 가격 확인일과 종료 예고 여부를 함께 적는다.** 위 가격은 2026-09-13 조사 기준이고 종료 예고는 **미확인**이다.

### 5-4. pgvector 를 기각한 이유

| | pgvector | JSON + 인메모리 |
|---|---|---|
| 300~1,000구절 검색 속도 | 수 ms | 1ms 미만 (numpy 행렬곱) |
| 메모리 | DB 쪽 | 1.8~6MB (컨테이너 512Mi 안) |
| 필요한 것 | 확장 설치, 인덱스 파라미터, alembic 마이그레이션, 백업 대상 확대 | 파일 하나 |
| 구절 수정 배포 | DB 마이그레이션 | 이미지 재배포 (리비전과 데이터 판이 같이 굴러가고, **롤백하면 데이터도 같이 돌아간다**) |
| 이길 수 있는 규모 | 10만 건 이상 | 1만 건까지 |

10초 가계부는 이미 Cloud SQL `db-f1-micro` 가 떠 있어 확장 설치 자체는 가능하다. 그런데 **그 DB 는 유일한 고정비**(월 1만5천원 안팎 추정)라 여기에 부하를 더할 이유가 없다. 경전 데이터는 사용자 데이터가 아니라 **코드에 가까운 정적 자산**이다. 코드와 같이 배포하는 것이 맞다.

## 6. 오남용 방지: 실패 네 가지와 막는 자리

### 6-1. F1 · 엉뚱한 구절이 붙는다

| 방어 | 층 |
|---|---|
| 태그 교집합 필터 | 코드 |
| `excluded_for` 하드 제외 | 코드 |
| `cautions` 를 후보와 함께 프롬프트에 싣는다 | 프롬프트 |
| LLM 이 **선정 이유 한 줄**을 돌려주게 하고 로그에만 남긴다 | 관측 |
| 주 1회 샘플 30건 사람 검수 | 운영 |

선정 이유를 로그에 남기는 것이 핵심이다. 오선정은 사용자가 신고하지 않는다(그냥 안 온다). 나중에 눈으로 훑을 재료가 없으면 영원히 못 잡는다. 10초 가계부 교훈 「사용자에게 이유를 안 알려 주기로 했으면, 우리한테는 남겨야 한다」.

### 6-2. F2 · 같은 구절만 반복된다

> **아직 아무것도 막고 있지 않다 (2026-09-15 확인).** 아래 원안 셋 중 코드에 들어간 것이 하나도 없다. 서버가 받는 것은 고민 글과 멱등키뿐이라(`ConcernRequest`) 최근 본 구절이 무엇인지 알 방법이 없고, 전역 노출 카운터는 00 X6 에서 「클라이언트 `Storage` 에서 온다」로 바뀌면서 서버 쪽이 비었는데 클라이언트 쪽도 아직 보내지 않는다. **같은 사람이 비슷한 고민을 이어 쓰면 같은 구절이 다시 올 수 있다.** 지금 막고 있는 것은 안전 규칙(어느 상태에서 어느 구절을 빼나)뿐이고, 그것은 반복과 다른 문제다.
>
> 지금 이것이 덜 아픈 이유는 후보 풀이 넓어졌기 때문이다. 16구절 판에서는 엄마를 잃고 자책하는 고민에 같은 구절이 다섯 번 전부 나왔고 팀에서 겉도는 고민에는 세 번 중 두 번이 같았다(5-2-1). 399구절 판에서는 고민마다 다른 구절이 붙는다(5-2-3 · 5-2-4 표). 다만 **회수율이 고친 것이지 반복 방지가 고친 것이 아니다.** 같은 사람이 같은 고민을 다시 쓰면 같은 구절이 다시 온다. 되살릴 때 드는 것만 적어 둔다: 기기 `Storage` 에 최근 구절 id 20개 · 요청에 그 목록을 싣는 칸 · `candidates()` 에서 제외하는 줄. 셋 다 구절 id 만 오가므로 고민 내용은 서버로 가지 않는다.

원안(기록):

- 익명키 단위로 **최근 노출 구절 id 20개**를 저장하고, 상위 10개를 후보에서 제외한다.
- 전역 노출 횟수 역가중을 점수에 넣어 특정 구절 쏠림을 막는다.
- **주의:** 이 저장은 PRD 20절의 Premium 「지난 고민 저장」과 다르다. 저장하는 것은 **구절 id 뿐**이고 고민 내용이 아니다. 개인정보가 아니므로 무료 사용자에게도 적용한다. 이 구분을 개인정보 처리방침에 한 줄로 적는다.
- 10초 가계부 교훈 「나중에 필요할 값을 해시로만 저장하면 그 기능이 통째로 막힌다」: 구절 id 는 해시하지 않는다.

### 6-3. F3 · 고민 유형별 커버리지 구멍

> **실제로 선 게이트는 아래 원안과 다르다 (2026-09-15 확인).** 원안은 태그당 개수와 난이도 분산을 셌는데, 시드에 `difficulty` 칸이 없고 태그가 테마 하나로 합쳐져서(3-1-1절) 그대로는 못 센다. 지금 `domains/scripture/gate.py` 가 **빌드와 기동에서 같은 검사를 돌리며** 보는 것은 넷이다.
>
> | 검사 | 무엇을 보나 |
> |---|---|
> | `check_quotable` | 구절마다 `source_work` · `canonical_location` · `speaker_kind` · `text_type` · 번역문이 차 있나. 운영 판에서는 `review.status=approved` 까지. 합성글·요약글이 섞였나 |
> | `check_context_vocabulary` | spec 의 `ContextFlag` 5종이 **전부 안전 규칙에서 뜻을 갖나.** 모델이 신고했는데 아무것도 안 막는 값이 있으면 실패 |
> | `check_every_flag_bites` | **깃발마다 실제로 빠지는 구절이 있나.** 풀 모드와 상관없이 시드 399구절 전체로 잰다. 규칙만 서 있고 걸리는 구절이 없으면 그 규칙은 도는 척만 하는 것이다 |
> | `check_safety_leaves_candidates` | 상태가 겹쳐도 후보가 남나. 다 빠지면 맞지도 않는 구절을 대신 내보내지 않고 기동에서 멈춘다 |
>
> **태그별 최소 개수 게이트는 아직 없다.** 감수 통과가 16구절뿐이라 지금 켜면 어느 테마도 12를 못 채워 기동이 통째로 막힌다. 출시 하한인 감수 200구절에 가까워질 때 다시 본다. 그때까지 커버리지 구멍은 게이트가 아니라 골든셋 회수율(5-2-1 · 5-2-4 표)로 본다.

원안(기록). **빌드 게이트로 막는다.** 데이터 빌드 스크립트가 아래를 검사하고, 하나라도 못 채우면 **빌드를 실패시킨다.**

```
태그 10종 각각:
  approved 구절 ≥ 12
  그중 difficulty=easy ≥ 4      (Basic 답변용)
  그중 difficulty=deep ≥ 2      (Deep 답변용)
universal 풀 ≥ 20
모든 구절: review_status=approved, retrieval_text 길이 ≥ 60자
citation_ko 의 절 번호가 ref.sc_uid 와 일치
```

⚠ 이 게이트가 진짜로 도는지는 **한 태그를 일부러 비워 빌드가 실패하는지 한 번만 확인한다.** 회차마다 하지 않는다. 10초 가계부에서 「배선을 끊어도 초록인 자리」를 세 개 만든 전례가 있다.

### 6-4. F4 · LLM 이 경전을 지어낸다 (PRD 6절 위반이 실제로 일어나는 자리)

이게 제일 중요하다. 프롬프트에 「지어내지 마세요」라고 쓰는 것으로는 안 막힌다.

| 방어 | 내용 |
|---|---|
| **계약으로 막는다** | LLM 출력 스키마에서 `scripture` 객체를 **없앤다.** `scriptureId` 문자열 하나만 받는다 |
| **화이트리스트로 막는다** | `scriptureId ∈ 이번에 우리가 준 후보` 가 아니면 거절. 1순위로 강제 치환하고 `scripture_fallback` 로그 |
| **조립을 서버가 한다** | `ko.text`, `citation_ko`, `terms` 는 전부 DB 값. 응답 경로가 한 곳이라 뚫릴 입구가 없다 |
| 본문 오염은 프롬프트 + 샘플 감사 | `personalAnalysis` 안에 새 「부처님 말씀」 인용이 끼는 것은 정규식으로 잡으면 거짓양성이 많다. **MVP 에서는 자동 검출하지 않는다.** 프롬프트로 금지하고 주 1회 샘플로 본다 |

⚠ 마지막 줄은 **미완이다.** 숨기지 않고 적는다. 「가릴 수 없는 것은 감추지 말고 적는다」(10초 가계부 M5).

PRD 28절의 출력 구조는 이렇게 바뀐다.

```diff
- "scripture": { "source": "...", "chapter": "...", "text": "..." },
+ "scriptureId": "dhp.223",
+ "scriptureReason": "상사에게 되갚고 싶은 마음이 고민의 중심이라 맞대응 구절을 골랐다",
```

`scripture` 객체는 **서버가 응답 조립 단계에서 DB 값으로 채워 클라이언트에 내려준다.** 클라이언트 계약은 PRD 28절 그대로 유지된다.

### 6-5. 폴백 사다리

| 단계 | 조건 | 행동 |
|---|---|---|
| 0 | `safetyFlag` (자해·자살·타해) | **경전 검색·LLM 답변 생성을 하지 않는다.** 고정 안내 화면 + 자살예방상담 109 안내. 이 화면에는 광고를 붙이지 않는다 |
| 1 | 후보 ≥ 3 | 정상 경로 |
| 2 | 후보 1~2 | `tags.secondary` 까지 확장해 다시 검색 |
| 3 | 후보 0 | `universal` 풀 20개에서 선택 (무상, 자애, 지금 이 순간처럼 어느 고민에나 서는 구절) |
| 4 | `universal` 도 실패 (사실상 없음) | 답변을 만들지 않는다. 「지금은 답을 드리기 어려워요, 조금 뒤에 다시 시도해 주세요」 + 재시도 버튼 |

⚠ 4단계에서 **경전 없이 LLM 답변만 내보내지 않는다.** 그건 PRD 6절이 막으려던 바로 그 상태다.

### 6-6. 남용 방어 (사용량)

PRD 19절의 하루 3회 제한만으로는 부족하다. 10초 가계부 교훈 「하루 상한은 몰아치기를 못 막는다」: 하루 300회 상한을 몇 초 만에 태울 수 있었다.

- 익명키당 **1분 창 3회**를 함께 둔다. 사람은 1분에 고민 세 개를 쓰고 답을 읽을 수 없다.
- **성공한 생성만 센다.** LLM 이 실패해 5xx 가 난 것을 다시 시도하는 길은 열어 둔다.
- 요청 본문 상한을 **인증보다 바깥의 ASGI 미들웨어**로 막는다. FastAPI 는 의존성을 풀기 전에 본문을 통째로 메모리에 올린다. 고민 텍스트 상한은 넉넉히 잡아도 20KB면 충분하다.

## 7. 데이터 파이프라인

```
①수집 → ②정제 → ③선별 → ④번역 → ⑤태깅 → ⑥감수 → ⑦빌드 → ⑧검증 → ⑨배포
```

| 단계 | 하는 일 | 누가 | 산출물 |
|---|---|---|---|
| ① 수집 | `bilara-data` published 브랜치를 **커밋 SHA 고정**해 clone | 스크립트 | 원본 JSON + SHA 기록 |
| ② 정제 | 세그먼트를 게송 단위로 합친다(`dhp1:1`~`dhp1:6` → 1게). 장 제목·인연담 분리 | 스크립트 | 정규화 레코드 423+ 건 |
| ③ 선별 | 감정 태그 10종에 맞는 후보를 고른다 | LLM 1차 → **사람 최종** | 300건 선별 목록 |
| ④ 번역 | 팔리 + 영역을 함께 주고 한국어 초벌 | LLM (빌드 타임) | `ko.text` draft |
| ⑤ 태깅 | `tags`, `themes`, `difficulty`, `modern_gloss`, `retrieval_text`, `cautions` 초안 | LLM | 필드 채워진 draft |
| ⑥ **감수** | 4-3 의 체크리스트 7개 | **사람 (필수 게이트)** | `review_status=approved` |
| ⑦ 빌드 | approved 만 모아 JSON 번들. 커버리지 게이트 실행 | 스크립트 | `scriptures.v1.json` |
| ⑧ 검증 | 골든셋 30건 회귀 | 스크립트 | 리포트 |
| ⑨ 배포 | 번들을 컨테이너 이미지에 동봉해 Cloud Run 리비전으로 | 배포 스크립트 | 리비전 |

### 7-1. 사람이 반드시 봐야 하는 지점 세 곳

| 지점 | 왜 | 안 보면 생기는 사고 |
|---|---|---|
| **P1 번역 정확성** (④ 뒤) | LLM 은 그럴듯한 오역을 만든다. 팔리 특유의 용어(`saṅkhāra`, `taṇhā`)는 영역에서 이미 한 겹 해석이 들어가 있다 | 교리적으로 틀린 문장이 「부처의 말」이라는 이름으로 나간다. 이건 제품 이름 자체를 깨뜨린다 |
| **P2 태그와 실제 맥락의 일치** (⑤ 뒤) | 표면 단어로 태깅하면 맥락이 뒤집힌다. 법구경의 「죽음」 게송을 `loss` 에 붙이면 자살 고민 사용자에게 최악으로 간다 | 위험한 매칭 |
| **P3 `cautions` 작성** (⑤ 뒤) | 이 구절을 **어떤 고민에 붙이면 안 되는가**는 LLM 이 잘 못 본다. dhp.365 가 출가 수행자 대상이라는 것 같은 맥락 | 피해자 탓하기, 구조적 부당함을 개인 마음 문제로 돌리기 |

⚠ P3 는 실제 예시가 이미 나왔다. **dhp.365 원문은 「비구(mendicant)」에게 한 말**이다. 한글 번역에서 수행자를 지우고 일반화했으니 그 사실을 `cautions` 에 남겨야 한다. 이걸 안 남기면 다음 사람이 「왜 원문과 다르지?」라고 되묻거나, 더 나쁘게는 원문 그대로인 줄 알고 인용한다.

### 7-2. 골든셋 (⑧ 검증)

고민 문장 30개를 손으로 쓰고, 각각에 **기대 태그**와 **와도 되는 구절 id 집합**을 적는다.


### 7-3. 갱신 주기

- 구절 추가·수정은 **월 1~2회 배치**. 리비전과 함께 간다.
- `status: retired` 로 내리고 **지우지 않는다.** 이미 나간 답변의 출처가 깨지면 안 된다.
- 10초 가계부 교훈 「지우지 말고 이름을 옮긴다」.

## 8. 앱인토스 제약과의 접점

이 축은 대부분 서버 쪽이라 SDK 와 직접 부딪히는 자리가 적다. 그래도 셋은 걸린다.

| 제약 | 근거 | 이 축에 미치는 영향 |
|---|---|---|
| **SSR 금지, CSR/SSG 만** | 플랫폼 규칙 원문 | 검색은 전부 서버 API. 문제 없음 |
| **번들은 `ait deploy` 로 배포** | 개발 사실 노트 | **경전 데이터를 미니앱 번들에 넣지 않는다.** 구절 하나 고칠 때마다 번들 배포와 심사가 걸리면 갱신이 막힌다. 서버가 맞다 |
| **광고 위치 2 「광고 보고 다른 가르침 보기」** (PRD 18절) | PRD | 검색 설계에 직접 영향. **1회 검색에서 후보 5개를 뽑아 세션에 들고 있다가, 리워드 광고 뒤에 2순위를 낸다.** 재검색 호출이 필요 없다. LLM 2차 호출만 추가된다 |

⚠ **종교 콘텐츠에 대한 앱인토스 심사 기준은 확인하지 못했다.** 플랫폼 규칙 노트(2026-09-11 확인)에 종교 관련 조항이 없고, 검색으로도 못 찾았다. **미확인**으로 열린 질문에 남긴다.

## 9. 10초 가계부 교훈을 어디에 적용했나

| 교훈 | 적용한 자리 |
|---|---|
| 화면이 막는 규칙은 화면을 안 지나는 입구에서 뚫린다 | LLM 에게 원문을 아예 안 받는다(6-4). `cautions`(프롬프트)와 `excluded_for`(코드)를 나눴다(3-1) |
| 조사 결과를 그대로 믿으면 안 된다 | 라이선스를 검색 요약이 아니라 **`LICENSE.md` 원문·GitHub API 응답**으로 확인했다. 못 확인한 것(팔리 판본, 동국역경원)은 미확인으로 적었다 |
| 「명시 금지 아님」을 방패로 쓸 수 없다 | 동국역경원 자료를 「금지 문구가 없으니 써도 된다」로 처리하지 않았다 |
| 검증 스텁을 만들면 그 스텁만 보고 안심하게 된다 | 골든셋 없이 임베딩을 켜지 않는다(5-2) |
| 배선을 끊어도 초록인 자리 | 커버리지 게이트를 일부러 깨뜨려 한 번 확인한다(6-3) |
| 값은 결정 요인이 아니라던 것이 사흘 만에 결정 요인이 됐다 | 임베딩 ADR 에 **가격 확인일과 종료 예고**를 함께 적는다(5-3) |
| 「키를 넣었다」와 「부를 수 있다」는 다르다 | 임베딩을 켤 때 배포 전 **실호출 연기 검사** 한 줄을 넣는다 |
| 나중에 필요할 값을 해시로만 저장하면 그 기능이 통째로 막힌다 | 노출 이력의 구절 id 를 해시하지 않는다(6-2) |
| 하루 상한은 몰아치기를 못 막는다 | 1분 창 3회를 함께 둔다(6-6) |
| 사용자에게 이유를 안 알려 주기로 했으면 우리한테는 남겨야 한다 | `scriptureReason` 을 로그에만 남긴다(6-1) |
| 지우지 말고 이름을 옮긴다 | `status: retired`(7-3) |
| 가릴 수 없는 것은 감추지 말고 적는다 | 본문 오염 자동 검출을 MVP 에서 안 한다고 명시(6-4) |

## 10. PRD 와 어긋나는 지점

| PRD | 어긋남 | 제안 |
|---|---|---|
| 28절 LLM 출력 구조 | `scripture: {source, chapter, text}` 를 LLM 이 돌려주는 형태다. **이 계약 그대로 두면 6절이 뚫린다** | LLM 계약을 `scriptureId` + `scriptureReason` 으로 바꾸고, 서버가 `scripture` 를 DB 값으로 채워 클라이언트에 내려준다. **클라이언트 계약은 그대로 유지된다** |
| 6절 「AI 가 경전을 만들지 않는다」 | 한글 번역을 LLM 초벌 + 사람 감수로 만드는 것이 이 원칙과 부딪히는 것처럼 읽힌다 | 원칙을 **「런타임에 LLM 이 경전을 생성하거나 선택 범위 밖의 문자열을 내지 않는다」**로 좁혀 적는다. 빌드 타임 번역은 사람 감수 게이트가 붙으므로 허용. 이걸 안 적어 두면 다음 회차가 「번역도 LLM 이 했으니 규칙 위반」이라고 읽는다 |
| 8절 「경전 원문 / 한역 / 번역문」 확장 | 팔리 원문 라이선스가 미확인이고, 초기불교 팔리 문헌에는 **한역이 없다** | MVP 는 「번역문 + 출처」만 낸다. 원문 보기는 라이선스 확인 뒤 2차. 한역은 대승 경전을 넣을 때 |
| 27절 Basic 경전 1개 / Deep 1~2개 | Deep 에서 2개를 내려면 서로 결이 다른 구절이 태그당 필요하다 | 태그당 최소 12개 기준으로 충족된다. 다만 **두 구절이 같은 말의 반복이 되지 않게** LLM 2차 패스에 「서로 다른 각도여야 한다」를 명시 |
| 25절 「오늘의 말씀」(매일 하나씩) | 고민과 무관한 일일 구절이라 별도 큐레이션이 필요하다 | `daily_pool` 플래그를 스키마에 추가한다. 300구절 중 `difficulty=easy` 이고 `cautions` 가 빈 것 60개 정도를 풀로 돌린다 |
| 20절 Premium 「지난 고민 저장」 | 반복 방지용 노출 이력 저장과 혼동될 수 있다 | 저장 대상이 **구절 id 뿐**이고 고민 내용이 아님을 개인정보 처리방침에 분리해 적는다 |

## 11. 미확인·열린 질문

1. **팔리 원문(Mahāsaṅgīti Tipiṭaka Buddhavasse 2500)의 라이선스.** `suttacentral.net/licensing` 이 봇 차단으로 안 읽혔다. SuttaCentral 포럼(`discourse.suttacentral.net`)에 직접 묻거나, 사람이 브라우저로 그 페이지를 열어 확인해야 한다. 확인 전에는 팔리 원문을 화면에 싣지 않는다.
2. **동국역경원 한글대장경의 이용 조건.** 사이트 인증서 오류로 직접 조회 실패. 공공누리 유형 표기가 있는지, 서면 이용 허락 절차가 있는지를 불교학술원 ABC 사업단에 문의해야 한다. 허락이 나오면 4-2절의 대승 경전 확장이 열린다.
3. **CBETA 한문 대장경 이용 조건.** 아함경·금강경 한역을 넣으려면 필요하다.
4. **감수자 확보와 단가.** 구절당 3,000~5,000원은 근거 없는 추정이다. 실제 견적을 받아야 한다. 사찰·불교대학 협력 가능성도 미확인.
5. **앱인토스의 종교 콘텐츠 심사 기준.** 플랫폼 규칙 노트에도 없고 검색으로도 못 찾았다. 콘솔 등록 전에 앱인토스에 직접 문의하는 편이 안전하다.
6. **임베딩 모델의 종료 예고.** `text-embedding-3-small` 과 `gemini-embedding-001` 의 지원 종료 일정을 확인 못 했다. 임베딩을 켜는 시점에 다시 본다.
7. **`universal` 풀 20구절을 어떻게 고르나.** 어느 고민에나 서면서도 「아무 말」이 되지 않아야 한다. 감수자와 함께 정해야 하는 자리다.
8. **다중 태그 고민에서 구절을 몇 개 낼까.** PRD 27절은 Deep 1~2개인데, 태그가 4개 나온 고민에서 구절 2개가 충분한지는 실제 답변을 만들어 봐야 안다.
